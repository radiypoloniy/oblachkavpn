# Архитектура прототипа

```text
MainWindow (WPF, обычный пользователь)
  ├─ Subscriptions → ограниченный HTTPS / разбор JSON, URI, Base64
  ├─ Profiles / SingBoxProfiles → проверки → один outbound + CoreKind
  ├─ RecoveryPolicy → бюджет восстановления процесса
  └─ ITunnelController → Engine → CoreAdapter → Windows Job → отдельный Xray / sing-box
                          stdin: JSON в памяти
                          127.0.0.1:стабильный порт сессии → SOCKS5 → сервер

LabCommand → LabPlan → LabRunner → тот же Engine → обезличенные JSON / CSV
```

## Границы ответственности

`Profiles` не переносит полную конфигурацию сервиса в локальный клиент. Он принимает один outbound, проверяет TLS и ограничения прототипа. `RuntimeConfig` создаёт собственный loopback inbound и единственный outbound. Это исключает скрытый переход на DIRECT внутри созданного SOCKS; общей гарантии для всех программ Windows из этого не следует.

`Subscriptions` занимается только получением и разбором списка подключений. Панель Remnawave не вызывается с административными полномочиями. Клиенту нужна пользовательская HTTPS-подписка, а не API-токен администратора панели.

`Engine` владеет только собственным процессом. Перед запуском выполняет проверку конфигурации: Xray `run -test -c stdin:` или sing-box `check -c stdin`. `CoreAdapter` хранит различия синтаксиса команд и локальной конфигурации. Запуск/отмена/Job Object/готовность SOCKS/проверка HTTP общие. Сырые логи не показываются и не сохраняются. Состояние Verified относится к последнему успешному запросу, а не к постоянно измеряемой живости.

`ProcessJob` связывает срок жизни Xray с процессом приложения. `RecoveryPolicy` ограничивает число повторов. Этот механизм не восстанавливает системные маршруты: на нынешнем этапе приложение их не создаёт.

`MainWindow` отображает состояния и выполняет явные действия пользователя. Список событий ограничен памятью; отчёт исключает серверные параметры. ClientStateStore сохраняет профили и ссылки через Windows DPAPI при включённом запоминании. Постоянная папка приложения общая для сборок; загрузка повторно проверяет профили и не запускает ядро. Тесты используют отдельное хранилище, не читают сохранения пользователя.

## Второе ядро и небольшие модули

`Profile` содержит явный `CoreKind`; отпечаток учитывает ядро. Нативные outbounds сохраняются без преобразования. XHTTP остаётся на Xray. Нельзя автоматически превращать произвольный Xray JSON в sing-box JSON: совпадение названий транспортов не гарантирует поддержку конкретных параметров.

WPF partial-файлы — явные части одной view: состояние/подключение, импорт, диагностика и UI fixtures. Это разделение представления, не отдельные сервисы. Независимые алгоритмы (подбор, бюджет восстановления, зеркала, стенд) находятся в отдельных классах и проверяются без WPF. Лимит сборки — 250 строк / 24 КиБ на исходник, включая будущие подкаталоги; obj/bin исключены. При дальнейшем росте извлекать ответственность в класс, а не обходить лимит минификацией.

`LabRunner` имеет узкие зависимости Start/Probe/Stop, ограниченный бюджет и гарантированную остановку в finally. Отчёт содержит индексы, ядро, классификацию и время; не содержит outbound, адреса или текст исключения. Перезапуск ядра перед каждым образцом даёт замер холодного соединения. Это первый стенд, не долгосрочный мониторинг.

## Что выделить перед TUN

Привилегированный helper должен иметь узкие команды и проверять запросы контроллера. Серверные UUID, токены подписки и любые произвольные JSON-конфигурации не должны быть API helper. UI остаётся без прав администратора. До разработки определить, кто владеет TUN-интерфейсом, какие изменения маршрутов/DNS допустимы и кто восстанавливает их при аварии.

Для восстановления записывать журнал только собственных сетевых изменений; не собирать широкие сведения о личной системе. Тесты выполнять на Windows VM со снимком. Настройки рабочего Throne и пользовательские подключения не использовать как скрытый источник конфигурации.

С версии 0.6.1 окно и RouteSearch используют ITunnelController. NetworkHelperContracts проверяет только будущие Acquire/Release-запросы с точными IP и loopback-портом; выполнение системных изменений ещё отсутствует. Конкретные границы и последовательность реализации описаны в [SYSTEM-TUN-ARCHITECTURE.md](SYSTEM-TUN-ARCHITECTURE.md).


В 0.6.2 NetworkSession управляет транзакцией через INetworkSessionJournal и INetworkSessionBackend. NetworkSessionJournal хранит ограниченный журнал и блокирует второго владельца файла. Пока есть только тестовый backend в памяти: рабочий Engine не применяет системные изменения. Сценарии восстановления описаны в [NETWORK-SESSION-0.6.2.md](NETWORK-SESSION-0.6.2.md).
