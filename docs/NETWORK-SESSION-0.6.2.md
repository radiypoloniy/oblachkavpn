# Сетевая сессия и откат — 0.6.2

Первый этап системного VPN реализован как отдельная библиотечная часть клиента. Окно продолжает использовать прежний SOCKS-контроллер. Новые классы не подключены к рабочему сетевому режиму: реального Windows backend пока нет.

## Состав

- `NetworkSessionModel.cs`: состояния, модель ограниченного плана, интерфейсы журнала и backend, проверка структуры.
- `NetworkSessionJournal.cs`: один явно заданный файл, эксклюзивная блокировка владельца, запись временного файла с Flush(true) и замена основной записи. Повреждённый файл не удаляется. Неудачно заменённые pending-файлы остаются для диагностики.
- `NetworkSession.cs`: запуск транзакции, отключение по LeaseId и восстановление незавершённой сессии. Один общий SyncRoot журнала сериализует контроллеры в процессе; файловая блокировка препятствует второму владельцу того же пути.
- `SelfTests.Network*.cs`: сетевой backend в памяти, инъекция аварий и отдельные файловые журналы в тестовой папке.

Журнал ограничен 64 КиБ и 32 изменениями. Отсутствующие, повторные и неизвестные JSON-поля, неизвестные состояния и некорректные значения отклоняются. Каталоги пользовательских подключений не сканируются.

## Применение

`Acquire` принимает проверенный запрос версии 1. Незавершённая прежняя сессия блокирует новый запуск. Backend без побочных эффектов готовит план только затрагиваемых ресурсов в порядке: исключения входного узла → интерфейс → маршруты → DNS. `Prepare` сохраняется до первого изменения.

После каждого применения записывается подтверждение Applied соответствующего шага. Только после завершения всех шагов вся сессия получает Applied. Отмена и ожидаемая ошибка запуска инициируют восстановление; отменённый токен не передаётся в очистку.

Если процесс погиб после изменения, но до подтверждения, в журнале шаг остаётся Planned. Поэтому восстановление проверяет все ещё не восстановленные намерения, включая Planned. Backend определяет по текущему значению и владельцу, было ли изменение применено.

## Восстановление

Перед очисткой сохраняется Restoring. При отказе этой записи новые изменения не выполняются. Шаги отменяются в обратном порядке, после каждого сохраняется Restored. Повторная очистка пропускает подтверждённые шаги; уже восстановленный шаг без подтверждения backend распознаёт как Unchanged.

При совпадении текущего значения с внесённым и подтверждении владельца backend возвращает прежнее значение. При чужом изменении он ничего не записывает и возвращает Conflict. Сессия становится RecoveryRequired, дальнейшее удаление зависимостей останавливается. Ошибка системной операции также оставляет RecoveryRequired. Повторный вызов продолжает очистку после устранения причины. Только полностью восстановленная сессия становится Released.

`Release` с другим LeaseId отклоняется. Повторный Release завершённой сессии не меняет сеть. `Recover` предназначен для будущего helper при запуске или потере владельца; это не доступная без аутентификации IPC-команда.

## Проверки

Аварии имитируются до и после всех четырёх применений и восстановлений, а также каждой записи журнала при запуске и очистке. Проверяются обычный откат, отмена, ошибки записи, ошибки backend, конфликт с чужим DNS, повторный запуск координатора, открытие файлового журнала новым владельцем, два конкурирующих контроллера, занятый файл и повреждение данных. Все сетевые значения синтетические; Windows DNS и маршруты не читаются и не меняются.

## Что требуется для Windows helper

Текущий backend — контракт поведения, не доказательство атомарности Windows API. Реальная реализация должна проверять принадлежность объектов, выводить идентификаторы и допустимые значения локально и обрабатывать гонки с внешними изменениями. Проверка формата журнала не заменяет его ACL, проверку отправителя IPC или контроль целостности установки helper. Строки Before/After — внутреннее представление доверенного backend, не параметры внешнего запроса и не место для ключей/подписок.

Журнал сохраняет намерение между перезапусками владельца, но сам не запускает восстановление после выключения питания. Будущий helper/служба должен вызывать Recover при старте до нового Acquire. Гарантии физической сохранности при потере питания и отката реальных ресурсов будут проверяться отдельно на Windows VM.

Следующий этап: ограниченный локальный IPC, проверка владельца сессии и обработка потери клиента. После этого — выбор готового TUN-механизма и реальный backend на отдельной VM.
