# Идея Oblachka и порядок реализации

Дата: 11 октября 2026 года. Исходный документ пользователя прочитан как предложение архитектуры. Его требования к этапам, Electron/Tauri и Android-форку не заменяют уже согласованное решение писать собственный клиент с готовыми ядрами.

## Что берём

Независимые маршруты, сохранение сторонних клиентов, отдельные тестовые inbound, раздельная выдача профилей по возможностям приложения и наблюдения из разных сетей. Remnawave остаётся управляющим слоем. Свой клиент можно развивать одновременно с лабораторией: это один контроллер запуска ядер и измерений, две разные пользовательские задачи.

В версии 0.3 реализована небольшая часть этой схемы: явные резервные ссылки подписки, обновление без разрыва активного туннеля, ограниченный ручной подбор соединения и стабильный SOCKS-порт в рамках запуска приложения. Боевые ноды и панель не менялись.

В 0.4 добавлены второй адаптер sing-box, нативные VLESS/Hysteria2 профили, переключение ядра с сохранением SOCKS-порта и ограниченный стенд с JSON/CSV. Передача через VLESS/TLS и Hysteria2/TLS проверена на loopback, не на операторских блокировках. Исходники разделены по ответственности; размер проверяется сборкой.

## Поправки к документу

1. Throne поддерживает Xray и sing-box, включая Xray VLESS и пользовательские конфигурации обоих ядер. Поэтому по названию оболочки нельзя определить поддержку Finalmask/VLESS Encryption. Проверяем точную версию движка, импорт и реальную передачу данных. [Официальный README Throne](https://github.com/throneproj/Throne#supported-protocols).
2. Оболочку Windows оставляем C#/WPF. Переход на Electron/Tauri сейчас не добавляет проверенную сетевую функцию. Android остаётся отдельным собственным интерфейсом с готовым core и VpnService; необходимость форка оценим при реализации этой платформы.
3. L0 — набор конкретных совместимых конфигураций, а не один переключатель «усилить защиту». Условия на клиенте и сервере и сочетания протокола/транспорта/защиты проверяются для закреплённой версии. Часть комбинаций недопустима. [Транспортные слои Project X](https://xtls.github.io/config/transport.html).
4. Текущий клиент требует TLS/REALITY. VLESS Encryption без TLS из предложенной матрицы требует отдельного лабораторного режима с проверкой параметров encryption; разрешать обычный VLESS/none вместе с ним нельзя.
5. «500 клиентов» и размеры сквадов — исходные гипотезы. Решение зависит от нагрузки, числа общих точек отказа, стоимости и наблюдаемых блокировок. Общий физический хост, ASN, CDN или домен могут связывать сквады, даже если IP различаются.
6. Падение узла на всех операторах не доказывает утечку IP. Подобные наблюдения дают гипотезы; нужны отдельные проверки DNS, TCP, TLS, авторизации, самого сервера и контрольного сайта. Автоматически объявлять сигнатуру или виновного пользователя нельзя.
7. Адрес входа доступен подключающемуся клиенту. Разделение групп и резервные адреса сокращают последствия отказа; не делают этот адрес невидимым. Для скрытия origin через промежуточный слой отдельно проверяются транспорт, выдача DNS и конфигурация этого слоя.

## Следующие итерации

**Развитие лаборатории.** Базовые адаптеры и повторяемый прогон уже работают. Далее: несколько контрольных адресов, длинные загрузки, ручные метки оператора и сравнение реальных сетей. Аппаратные идентификаторы и личные настройки автоматически не собираются. Инструкция текущего стенда — `LAB.md`.

**TUN Windows.** Проверка на отдельной VM, определение владельца интерфейса, исключение точки входа из маршрута, DNS/IPv6/UDP, восстановление после штатной и аварийной остановки. Далее системный kill switch с проверкой поведения при отказах. Рабочая сеть пользователя не является испытательным стендом.

**Восстановление соединения.** Несколько контрольных сайтов, несколько последовательных отказов, ограничение частоты переключений, отмена по Stop, отсутствие DIRECT. Подбор 0.3 — основа этой политики, но сейчас запускается только по кнопке и не обеспечивает постоянный мониторинг.

**Профили сервиса.** Версионированная модель capabilities и нормализованных узлов поверх Remnawave, метаданные срока/трафика, явное защищённое хранение токенов. Резервные ссылки сначала только вручную; автоматическая доставка списка резервов требует проверки происхождения, например подписи конфигурации.

**L0 и мониторинг.** Отдельная тестовая нода и измерения минимум в трёх мобильных сетях. Только после воспроизводимых результатов — малый тестовый сквад. Возможности Response Rules позволяют выделить выдачу нашего клиента. [Документация Remnawave](https://docs.rw/learn-en/routing-rules/).

**L1.** Исследовательская ветка и отдельные версии клиента/сервера, когда измерения показывают конкретную нерешённую проблему. Совместимость, откат и ограниченный круг тестировщиков — до публичной выдачи. Название новой маски не является доказательством устойчивости.

Исходные рыночные оценки, цены и юридические выводы о Европе/сторах этой реализацией не подтверждаются и требуют отдельной актуальной проверки, если будет принято решение о таком запуске.
