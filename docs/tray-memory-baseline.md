# Память в трее: проверка освобождения окна

Дата: 2 ноября 2026 года. Пользователь сообщил, что пробная сборка по-прежнему занимает
около 85 МБ в трее. В этой сборке окно скрывается, а не освобождается. Ранее измеренное
снижение выделений памяти не подтверждает снижение постоянной RAM в этом сценарии.

## Стенд

`TrayMemoryPreview` доступен только с `IncludeTestCode=true`. Три отдельных последовательных
процесса, два синтетических профиля, открытая и закрытая аналитика, настоящее WPF-окно.
В каждом процессе измеряются видимое окно, скрытое окно через 4 секунды, закрытое окно
через 6 секунд и отдельный образец после диагностической принудительной сборки мусора.
Владелец приложения, профиль и значок трея остаются живы. Ядро имитируется; реальный VPN,
реестр системного прокси, подписки и обращения во внешнюю сеть не используются.

Это оценка эффекта закрытия окна, а не готовый режим работы клиента без окна. Счётчики
трафика и другие оставшиеся фоновые функции ещё не перенесены. Сценарий не воспроизводит
конфигурацию пользователя и не объясняет точное происхождение его 85 МБ.

## Результат

Медианы трёх запусков, МиБ = 1024² байт:

| Состояние | Приватная память процесса | Частный рабочий набор | Управляемая память |
| --- | ---: | ---: | ---: |
| Видимое окно | 81,52 | 44,66 | 10,79 |
| Скрытое окно | 79,75 | 43,81 | 10,80 |
| Закрытое окно, без принудительного GC | 77,90 | 40,90 | 10,82 |
| Закрытое окно, диагностический GC | 73,93 | 36,99 | 3,89 |

Разброс приватной памяти скрытого окна: 78,96–89,34 МиБ, после закрытия: 77,76–79,85 МиБ.
После диагностического GC: 73,74–75,58 МиБ. До принудительного GC слабая ссылка ещё
указывала на окно во всех трёх процессах; после него окно собрано во всех трёх.

Частный рабочий набор измеряется через `GetProcessMemoryInfo` и
[`PROCESS_MEMORY_COUNTERS_EX2.PrivateWorkingSetSize`](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters_ex2).
Он отличается от приватной выделенной памяти и полного рабочего набора. Управляемая
память — `GC.GetTotalMemory(false)`, а не полный объём памяти процесса и не точный размер
живых объектов до сборки мусора. Разные столбцы нельзя напрямую сравнивать с одной
неуточнённой цифрой диспетчера задач.

## Следствие для оптимизации

На этом стенде простое закрытие окна уменьшило медиану приватной памяти примерно на
1,85 МиБ относительно скрытого окна. Даже диагностическая полная сборка мусора оставила
около 74 МиБ. Это не основание обещать резкое уменьшение расхода в трее после завершения
переноса фоновых задач. Принудительный GC не добавляется в рабочий клиент; уменьшение
рабочего набора через вытеснение страниц также не является исправлением расхода памяти.

Для существенного следующего шага следует измерить минимального владельца подключения
и трея без загруженного WPF-интерфейса, затем сравнить вариант отдельного процесса окна.
Если процесс интерфейса завершается при скрытии, его память можно освобождать вместе с
загруженными компонентами, но перед таким изменением нужны замеры базового процесса,
проверка восстановления окна и сохранение всех фоновых функций. Экономия этого варианта
пока не измерена. Сам по себе перенос методов из MainWindow не считается результатом по RAM.

## Повторение

```powershell
.\build.ps1
.\test.ps1
.\scripts\MemoryProbe\TrayUi.ps1 -Executable .\out\test\Oblachka.exe -OutputFolder .\out\tray-memory
```

Исходные отчёты этого замера: `out/tray-memory-20261102/tray-{1,2,3}.json`, сводка:
`out/tray-memory-20261102/summary.json`. Файлы out не включаются в репозиторий.
Проверки: сборка без предупреждений, 370 логических и 62 интерфейсные успешно;
тестовый стенд отсутствует в поставляемой сборке. Рабочее поведение в этой правке не меняется.
