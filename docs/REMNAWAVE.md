# Интеграция с Remnawave

## Результат прогона реальной подписки · 12 октября 2026

Проверена подписка тестового пользователя панели `sub.oblaconnection.com`. Прогон делался зондом `probe-subscription.ps1` и разбором `Oblachka.Tests.exe --import-check <файл> <отчёт> --validate`. Ссылка подписки в репозиторий не попадала.

**Правила Response Rules в панели уже есть, и менять их не нужно.** Ответ зависит от `User-Agent`: `Happ/*` получает JSON, остальные — Base64-список ссылок. Наш клиент попадает во вторую группу вместе с v2rayNG, и это оказался правильный для нас формат.

Что отдаёт Base64-список: 13 узлов, 12 VLESS и один Hysteria2. Транспорты TCP/REALITY, XHTTP/REALITY и XHTTP/TLS. **XHTTP `extra` передаётся прямо в параметре ссылки** — в двух узлах это `xmux` и полный набор padding-настроек. `downloadSettings` не используется ни в одном узле, а в ссылку он и не поместился бы. Прежнее утверждение документа, что ссылки непригодны из-за потери `extra`, для этой панели неверно.

Результат разбора: **импортировано 13 из 13, отклонённых нет, закреплённые Xray 26.9.9 и sing-box 1.14.3 приняли все 13 конфигураций.** Выдача Xray JSON нашему клиенту не нужна; шаблон Happ для нас хуже — в нём 47 outbounds, из них 27 неподдерживаемых, а имя узла одно на всю выдачу.

Заголовки панели: `subscription-userinfo` с `expire` и `total=0` (безлимит), `profile-title` и `announce` в виде `base64:`, `profile-update-interval`, `profile-web-page-url`, `support-url`, `routing` с политикой Happ. Клиент пока читает только `subscription-userinfo`.

## Балансировщик «Авто» и одинаковые конфигурации

«Авто — оптимальное подключение» и «Германия» (TCP) приходят клиенту полностью одинаковыми: один адрес `5.252.155.19:443`, один UUID, одни `pbk`, `sid`, `sni` и `flow`. Балансировка выполняется на серверной стороне, и по выдаче подписки клиент её увидеть не может — адрес задан числовым IP, так что даже разные ответы DNS тут ни при чём. Владелец подтвердил, что балансировщик работает как задумано.

Для клиента из этого следуют два требования, и оба выполнены:

1. Склейка дублей при импорте идёт по имени вместе с конфигурацией. Прежняя склейка только по конфигурации молча теряла вторую запись: импортировалось 12 узлов из 13 без единого сообщения об отказе.
2. Поиск записи в списке и восстановление выбора сначала сверяют имя вместе с отпечатком, и только потом один отпечаток. Так переименование узла в панели не теряет выбор, а две строки с одинаковой конфигурацией не подменяют друг друга. В снимке состояния рядом с `SelectedFingerprint` сохраняется `SelectedName`; снимки прежних версий читаются по-прежнему.

Отпечаток `Profiles.Fingerprint` остаётся независимым от имени: на этом держится устойчивость к переименованию, и это проверяется отдельно.

## Замечание к заголовкам панели

`support-url` указывает на `https://dummy.docs.rw` — значение по умолчанию. Запрос с браузерным `User-Agent` возвращает 502, то есть ссылка подписки, открытая в браузере, у пользователя не откроется. Своей поддержки у сервиса пока нет, поэтому `ServiceBrand.SupportUrl` пуст и кнопка поддержки не показывается.

Ниже — прежние проектные заметки.

Панель и рабочие серверы не изменялись. Клиент использует обычный GET пользовательской HTTPS-подписки с `User-Agent: RoutePilot/0.3`, а не административный API панели. Правило с префиксом `RoutePilot/` подходит и для 0.3. Теперь можно явно добавить до пяти полных резервных адресов; никакого переписывания токенов между доменами нет.

По [официальной документации шаблонов](https://docs.rw/learn-en/templates/) формат определяется по клиенту; Base64 служит запасным вариантом. Чтобы получать полный Xray outbound с XHTTP extra, для собственного клиента лучше явно настроить выдачу Xray JSON. Документация [Response Rules](https://docs.rw/learn-en/routing-rules/) позволяет сопоставить User-Agent с типом ответа и шаблоном.

В `oblachka-response-rule.example.json` сохранён пример **одного правила**, которое можно добавить в соответствующий список правил панели после проверки её версии. Оно не является конфигурацией всей панели и не должно заменять существующие правила. Порядок имеет значение: верхнее совпавшее правило определяет ответ. Здесь нет токенов, узлов и пользовательских данных.

На реальном тестовом пользователе проверить:

1. Конечный URL возвращает JSON/текст, а не HTML или redirect.
2. В JSON используются VLESS `settings.vnext` и транспорты, поддерживаемые Xray 26.9.9.
3. Сохранились XHTTP path/mode/extra/downstream, REALITY SNI/pbk/sid и flow.
4. Набор узлов и сроки доступа соответствуют тестовому пользователю.
5. Поведение ответа при истёкшей/отозванной подписке понятно клиенту.

Прототип пока не обрабатывает метаданные трафика/срока действия в заголовках, объявления панели, remote routing и HWID-регистрацию. Если панель требует HWID, эту возможность надо реализовать отдельно; не ослаблять правила для существующих пользователей ради прототипа. Возможный подход для будущей регистрации устройства — случайный идентификатор установки с явной регистрацией, без чтения аппаратных серийных номеров.

В текущую сборку импортируются только outbounds. Если шаблон зависит от DNS, routing, дополнительных outbounds или внешних файлов, его нельзя считать полностью поддержанным. Нужен отдельный клиентский шаблон для возможностей RoutePilot или следующий этап нормализации профилей.
