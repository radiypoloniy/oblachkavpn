# Системный VPN Windows: границы и порядок реализации

## Что уже работает в 0.6.1

`ITunnelController` отделяет окно и подбор подключений от реализации `Engine`. Интерфейс задаёт запуск, остановку, проверку через туннель, состояние и уведомления. `Engine` сохраняет управление Xray/sing-box, передачу конфигурации через stdin и Windows Job Object.

`NetworkHelperContracts` — чистый валидатор будущего запроса. Версия 1, непустой идентификатор сессии, Acquire/Release, loopback-порт и до 16 точных IP узлов. JSON ограничен 8 КиБ; неизвестные, отсутствующие и повторные поля отклоняются. Домены, CIDR, loopback, multicast, link-local, сокращённые IPv4 и повторные адреса отклоняются. Release не принимает сетевые параметры. В контракте нет UUID, подписки, конфигурации ядра, путей к executable или команд оболочки.

Это предварительная граница доверия. Сейчас нет IPC, привилегированного процесса, TUN, системных маршрутов, управления DNS или firewall. Прохождение проверки запроса не даёт права изменять сеть: будущий helper отдельно проверяет отправителя, принадлежность сессии и допустимость операции.

## Целевая цепочка

```text
WPF / пользовательская сессия
    ↓ команды и состояния
TunnelController
    ├─ CoreAdapter → Xray / sing-box (без повышения прав)
    └─ NetworkSessionClient → ограниченный IPC
                                  ↓ проверка владельца
                            NetworkHelper
                                  ├─ журнал собственных изменений
                                  ├─ TUN / маршруты / DNS
                                  └─ точный откат и контроль срока сессии
```

Контроллер решает порядок запуска и остановки, отмену и проверку. Helper владеет системными изменениями и восстанавливает их независимо от окна. Полномочия администратора не нужны самому интерфейсу или процессу ядра.

Предварительный вариант — отдельный подписанный helper по запросу, с явным повышением прав при включении общесистемного режима. Windows service имеет смысл позже для автоподключения до входа пользователя и обслуживания установщика. Транспорт IPC — локальный named pipe с ограниченным ACL, проверкой идентичности клиента и привязкой каждой lease к владельцу; имя pipe само по себе не является аутентификацией.

## Выбор пути данных

Следующий технический эксперимент сравнивает готовый TUN sing-box с мостом TUN → локальный SOCKS для Xray. Сначала проверяются закреплённые бинарники на VM: IPv4/IPv6, TCP, UDP, DNS, MTU, отмена и восстановление. Наличие SOCKS5 сейчас доказывает только TCP; UDP не считать поддержанным до отдельного теста. Нативные XHTTP-профили остаются на Xray. Перевод произвольной конфигурации между ядрами не использовать.

От результата зависит владение TUN-интерфейсом и набор команд helper. Текущий Acquire не является завершённой схемой настройки TUN: версия контракта должна измениться, если понадобятся дополнительные строго определённые параметры. Нельзя добавлять произвольный JSON или команду запуска ради удобства интеграции.

## Жизненный цикл и восстановление

1. Контроллер валидирует профиль, разрешает адреса входного узла и запускает собственное ядро. Helper повторно проверяет адреса; endpoint-исключения относятся только к этому узлу и выбранному uplink.
2. Helper создаёт журнал намерения и сохраняет только параметры, которые собирается менять. Запись журнала подтверждается до каждого системного изменения.
3. Сначала устанавливаются исключения для входного узла, затем собственный интерфейс и маршруты/DNS. Только после проверки контроллер объявляет системный туннель готовым.
4. При обычном отключении helper отменяет собственные изменения в обратном порядке и подтверждает завершение; контроллер останавливает ядро. Точная последовательность зависит от выбранного TUN-механизма.
5. При потере IPC, истечении lease или аварии окна helper выполняет тот же откат. Если сам helper завершился, следующий запуск проверяет незавершённый журнал перед новой сессией. После отключения питания нужно восстановление при запуске helper/службы; пока приложения не запущены, обещать автоматический откат нельзя.

Журнал содержит идентификаторы собственных объектов, факт применения и прежние значения только изменяемых параметров. Он не содержит профилей, подписок или истории сайтов. Откат сверяет актуальное значение с внесённым: чужие последующие изменения нельзя затереть старым снимком всей сети. Частичный отказ оставляет запись для повторного восстановления и понятное сообщение.

Kill switch — отдельный этап: правила firewall с собственными идентификаторами и проверенным порядком удаления. Нельзя обещать «ничего не уйдёт мимо VPN», пока тесты утечек и аварий не подтверждают это. Умный режим также требует реальной политики DNS/маршрутов, а не только переключателя в UI.

## Последовательность следующих изменений

Первый пункт реализован в 0.6.2: модель сессии, файловый журнал и повторяемый откат на тестовом backend. Подробности и границы — [NETWORK-SESSION-0.6.2.md](NETWORK-SESSION-0.6.2.md). Следующий пункт — IPC и владелец сессии; реальный сетевой backend ещё не подключён.

В 0.7 реализованы IPC и координатор: [HELPER-IPC.md](HELPER-IPC.md), [SYSTEM-COORDINATOR.md](SYSTEM-COORDINATOR.md). Проверка TUN через check и комплект для отдельной VM готовы; [контрольные точки](MILESTONES-0.7.md) фиксируют коммиты и границу до реального Windows backend.

1. Модель сессии и журнал: Prepare → Applied → Restoring → Released/RecoveryRequired; тесты аварии между каждым шагом на подменном сетевом backend. На этом этапе сеть компьютера не изменяется.
2. Локальный IPC и проверка владельца: разрешённые операции, ограничения размера/времени, отмена, потеря клиента, чужой LeaseId, дубликат Acquire/Release. Проверка обеих сторон без привилегированных действий.
3. TUN-эксперимент и минимальный helper на отдельной Windows VM со снимком. Выбор проверенного пути для Xray и sing-box; фиксация возможностей TCP/UDP/IPv6.
4. Реальные маршруты и DNS через журнал: последовательный откат, смена uplink, падение процессов, сон/пробуждение, перезагрузка. Проверка отсутствия остаточных собственных объектов после остановки.
5. Интеграция состояния в UI, затем kill switch и правила маршрутизации. На рабочем соединении тестировать после прохождения матрицы VM.

## Состояние после 12 октября 2026

Пункт 3 выполнен: [результаты проверки на VM](VM-TUN-RESULTS-2026-10-12.md). Путь данных выбран — sing-box TUN с `auto_route` и `route_exclude_address`, Xray остаётся исходящим звеном через локальный SOCKS. Мост TUN → SOCKS отдельно не понадобился.

Открытый вопрос «владение интерфейсом и набор команд helper» закрыт результатом стенда: маршруты и DNS ставит и снимает само ядро, поэтому helper владеет не списком маршрутов, а процессом ядра и его сроком жизни. Контракт `Acquire`/`Release` менять не пришлось.

Реализовано:

- `WindowsTunnelBackend` — сетевой backend с одним изменением сессии: интерфейс туннеля вместе с процессом ядра. Чужой интерфейс с нашим именем даёт `Conflict`, отсутствие интерфейса при восстановлении считается успехом, застрявший адаптер поднимает `IOException` и переводит сессию в `RecoveryRequired`.
- `SingBoxTunnelProcess` — запуск ядра с конфигурацией через stdin под Job Object. Без задания ядро переживает смерть владельца: это наблюдалось на стенде.
- `NetworkHelperHost` — привилегированная половина. Из командной строки принимает только имя канала и идентификатор владельца; путь к ядру выводится из собственной папки сборки. Без прав администратора и без живого владельца не обслуживает никого.
- `NetworkHelperLauncher` — запуск с явным запросом прав (`runas`). Отказ пользователя в повышении прав — обычный ответ, а не сбой.

Не сделано: подключение системного режима к окну, kill switch и повторный прогон на VM уже с реальным helper. Пока helper собран, но приложение его не запускает.

Remnawave остаётся источником пользовательских подписок. Этот этап меняет клиентский сетевой слой и не требует переписывать серверную панель.
