# Экономия ресурсов ядра — 1 ноября 2026

## Изменения

Фоновый учёт использует компактную сводку по программам из собственного Go-ядра.
Полный Clash `/connections` остаётся у открытого экрана соединений и команд,
которым нужны идентификаторы, сайты и точные маршруты.

Сводка строится по уже существующим атомарным счётчикам sing-box. Дополнительных
обёрток TCP/UDP, операций на каждом пакете и фонового таймера в ядре нет.
Работа выполняется по запросу клиента. Сводка содержит накопленные байты,
количество соединений по маршрутам и время последнего наблюдения программы.
Домены и адреса в неё не входят.

Новый API — сервис `oblachka-programs` внутри того же процесса, на IPv4 loopback,
на порту рядом с существующим Clash API. Используется секрет той же сессии.
Клиент проверяет по таблице Windows, что оба слушателя принадлежат одному PID,
до передачи секрета. Занятый дополнительный порт не мешает запуску VPN.

Формат аренды службы не изменён. Если установленная служба ещё не умеет
собирать конфигурацию этого сервиса, клиент один раз выбирает прежний способ
учёта на всю сессию. После успешного включения сводки временный сбой запроса
не переключает источник: иначе возник бы двойной учёт трафика. Учёт через
полный список в старой службе сохраняется также при открытом экране соединений.

## Ограничения и точность

- До 256 программ на сессию, остальные — «Другие программы». Слишком длинные
  пути и пути с управляющими символами также попадают в эту сумму.
- Состояние соединений ограничено активными соединениями и закрытым окном
  sing-box, которое содержит последние 1000 закрытых соединений.
- Короткие соединения, закрытые между опросами, учитываются, если ещё находятся
  в этом окне. При переполнении окна сохраняются ранее наблюдённые байты;
  сводка не претендует на точный аудит всех соединений при произвольной нагрузке.
- Гонки закрытия и повторное получение закрытой записи не удваивают счётчик.
- Идентификатор эпохи отличает новый процесс ядра от старого даже тогда, когда
  новые счётчики уже больше прежних.
- Сброс аналитики выставляет новую базовую отметку: накопленные счётчики ядра
  не возвращают удалённую историю. Период журнала программ остаётся 10 минут.

## Одно ядро в выборочном режиме

При поддерживаемом прямом выходе режим «Через VPN только выбранное» больше не
держит дополнительный процесс ядра окна. Проверка связи использует именованный
VPN-переключатель через `/proxies/server-selector/delay`, а не итоговое правило
маршрутизации. Локальный тест проверяет отказ сломанного выбранного выхода при
работающем прямом итоговом маршруте и успех после выбора рабочего выхода.
TLS-проверка остаётся включённой; тестовый сертификат доверяется только процессом
Go-тестов. Фрагментация и другие условия, требующие отдельного ядра, сохранены.

## Стенды

`MemoryProbe --core-live` запускает настоящее ядро с локальным SOCKS-входом и
500 TCP-соединениями к локальному echo-серверу. Проверяются переданные байты
и их привязка к программе. Для каждого API выполняются пять прогревочных
запросов, затем три серии по 100 запросов. Измеряются размер ответа, время,
CPU процесса ядра и `runtime.MemStats.TotalAlloc`.

Также сохраняются приватная память, рабочий набор, Go-куча, стеки, количество
GC и горутин до нагрузки, под нагрузкой и после закрытия соединений.
HTTP `/runtime` требует тот же секрет и используется только диагностическим
стендом; обычный клиент его не опрашивает. Стенд не вызывает GC; штатный
`FreeOSMemory` после старта ядра сохранён.

```powershell
dotnet build scripts/MemoryProbe/MemoryProbe.csproj -c Release -o out/core-memory-probe --configfile src/NuGet.Config
out/core-memory-probe/MemoryProbe.exe --core-live out/app/tools/oblachka-core.exe out/core-stage3/core-live-default.json
out/core-memory-probe/MemoryProbe.exe --programs out/test/Oblachka.dll out/core-stage3/parser.json
```

Режим `--programs` сравнивает разбор полного ответа на 2000 соединений и сводки
на 100 программ: пять прогревов и 30 разборов, без принудительного GC.
Go-бенчмарк `BenchmarkProgramPoll` отдельно сравнивает синтетическое формирование
JSON аналогичной структуры и реальную функцию построения сводки.

Стенд loopback не измеряет TUN, скорость реального VPN, DPI, QUIC и потерю пакетов.
Суммарные выделения за серию не являются постоянно занятой оперативной памятью.
Часовой прогон и сравнение стеков TUN остаются отдельными измерениями.

## Параметры выполнения

Проверяются `GOGC=100`, `75`, `50`; результат оценивается вместе с CPU и GC.
Параметры GC в поставляемой сборке, MTU, стек TUN, DNS-кэш, проверки TLS,
маршрутизация и защита WFP не ослаблялись. Версии зависимостей Go сохранены;
обновлён только собственный код ядра и его закреплённый SHA256.

## Результаты финальной сборки

Настоящее ядро, 500 открытых TCP-соединений от одной программы. Медианы трёх
серий по 100 запросов каждого API в одном процессе, после прогрева:

| Показатель | Полный список | Сводка программ |
| --- | ---: | ---: |
| Размер одного ответа | 234 520 байт | 276 байт |
| Выделения ядра за 100 запросов | 246,68 МиБ | 12,00 МиБ |
| CPU ядра за 100 запросов | 1312,50 мс | 62,50 мс |
| Время серии из 100 запросов | 624,28 мс | 68,45 мс |

Выделения ядра на этом стенде уменьшились на 95,1%, CPU — на 95,2%.
Число программ важно: здесь 500 соединений принадлежат одному процессу.
Стенд подтвердил учёт 512 000 байт в каждом направлении.

Разбор в клиенте: 2000 соединений, 100 программ, медианы трёх отдельных
процессов по 30 разборов:

| Показатель | Полный список | Сводка программ |
| --- | ---: | ---: |
| Размер ответа | 460 707 байт | 11 163 байта |
| Выделения за 30 разборов | 37,50 МиБ | 0,72 МиБ |
| Время 30 разборов | 499,75 мс | 10,41 мс |

Выделения клиента при разборе уменьшились примерно на 98,1%.

Память процесса ядра в loopback-сценарии: 54,71 МиБ в простое, 72,34 МиБ
при 500 соединениях, 78,08 МиБ после серии запросов и 77,85 МиБ через две
секунды после закрытия соединений. Горутины: 12 → 1012 → 1013 → 13.
Это не замер экономии постоянной памяти относительно старого ядра: в одной
сессии последовательно нагружались оба API. Остаточное потребление после
нагрузки требует отдельного длительного профилирования.

Сравнение GC — по одному полному loopback-прогону на настройку; память и CPU
взяты к завершению серий опросов, CPU включает также старт и создание соединений:

| GOGC | Приватная память | CPU процесса с начала прогона | Число GC |
| --- | ---: | ---: | ---: |
| 100 | 78,08 МиБ | 6203,12 мс | 112 |
| 75 | 75,71 МиБ | 6765,62 мс | 166 |
| 50 | 72,31 МиБ | 10031,25 мс | 271 |

Для `GOGC=50` около 5,8 МиБ экономии сопровождались ростом CPU примерно на
61,7% в этом сценарии. Настройки GC по умолчанию не изменены. Сценарий
содержит интенсивный опрос полного API, поэтому сам по себе не определяет
оптимальный GC для обычной фоновой работы со сводкой.

Сырые отчёты: `out/core-stage3/core-live-*.json`, `parser-*.json`,
`go-benchmark.txt`; сводка — `out/core-stage3/summary.json`.

  авторизацию и независимость проверки VPN от прямого итогового маршрута.
- `build.ps1`: успешно, закреплённый бинарник ядра проверен.
- `test.ps1`: 339 проверок логики и 58 проверок интерфейса, все успешны.
- Проверено отсутствие тестового кода в поставляемой сборке.
- Итоговый SHA256 `oblachka-core.exe`:
  `1003EFC870B2B06602547DBCAE7DDAC3C8E95CA88CFA4F6571599D49BFCE2878`.

в `out/app`; испытания выполнялись отдельными процессами с синтетическими
конфигурациями и локальными адресами.
