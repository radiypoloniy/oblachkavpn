# Канал отдельного окна к фоновому владельцу

Исторический отчёт первого этапа (IPC v1). Продолжение с подключением, выбором сервера
и актуальным протоколом v2: [background-connections.md](background-connections.md).

Дата: 2 ноября 2026 года. Этот этап проверяет связь процессов, необходимую для освобождения
всего процесса интерфейса в трее. Основной клиент пока использует прежний MainWindow;
новый канал автоматически не запускается и не заменяет рабочее подключение.

## Контракт и время жизни

`ClientViewServer` обслуживает конкретный процесс окна через случайное имя локального
named pipe. Используются существующие ACL текущего пользователя и проверки PID обеих
сторон; дескрипторы процессов удерживаются до подключения. Старый или посторонний
процесс не может выдать себя за ожидаемую сторону. Имя канала не является доказательством
подлинности. Это пользовательский IPC, без запуска привилегированной службы или повышения прав.

Команды: `ReadState`, `Probe`, `Stop`. У владельца есть случайный InstanceId на весь срок
жизни ClientRuntime. Клиент сначала получает его, затем указывает при командах; команда
для другого экземпляра отвергается. Повторы последних 64 RequestId в соединении также
отвергаются. Запуск процессов, произвольные методы, URI проверок и конфигурации через
этот контракт не передаются. DTO состояния содержит только имя сервера (до 256 символов),
число профилей, состояния ядра/TUN, занятость, локальный порт и результат проверки связи.
В нём нет ссылок подписок, outbound JSON, UUID или паролей серверов.

Фреймы используют существующий ограниченный JSON-протокол (до 64 КиБ), который отвергает
неизвестные и повторные поля. Для ожидания запроса, исполнения и записи ответа выделены
отдельные сроки. Команды выполняются в SynchronizationContext владельца, а не в потоке IPC.
Проверка связи идёт через ClientHealthMonitor; остановка отменяет текущие операции, сначала
снимает TUN, затем останавливает ядро и восстанавливает прокси. Ошибка возвращается кодом,
без передачи текста исключений с возможными данными конфигурации.

Probe подтверждает запуск проверки, оставляя канал свободным; занятость и результат
читаются последующими ReadState. Stop в том же канале отменяет незавершённую проверку,
дожидается её завершения и останавливает ядро. Проверка принадлежит монитору, поэтому
закрытие её инициировавшего окна не отменяет её само по себе.

Потеря или закрытие окна завершает только канал. Сервер не владеет ClientRuntime и не
останавливает его при EOF. Уже запущенная проверка связи также переживает закрытие канала.
Новый процесс окна получает снимок того же владельца по новому каналу. Явная Stop
продолжает исполняться, даже если окно закрылось после отправки команды.

## Что проверено

Девять новых проверок покрывают строгий формат сообщений, состав снимка, чтение и
проверку связи, повторное подключение, неверный InstanceId, повтор команды, неверные PID
обеих сторон, отключение клиента во время проверки и снятие имитируемого TUN по Stop.
Отдельно проверена отмена медленной проверки связи командой Stop по тому же каналу.

Отдельный сценарий запускает четыре настоящих WPF-процесса: закрытие, принудительный
выход без Dispose, повторное открытие/закрытие, явная остановка кнопкой окна. Окно стенда
не создаёт свой ClientRuntime. Имитация ядра остаётся Running после первых трёх процессов
и переходит в Idle только после команды четвёртого. Во всех окнах совпадает InstanceId.

`ClientViewPreview` и его аргумент запуска доступны только в тестовой сборке. Они отсутствуют
в поставляемом клиенте; проверка отсутствия тестового кода дополнена этим типом. Это
минимальное окно проверки канала, а не перенесённый основной интерфейс со всеми функциями.

## Память фонового процесса

Три отдельных последовательных запуска `TrayProbe --views` используют production DLL
для владельца, настоящий трей, сохранение в отдельный зашифрованный файл и имитируемый
прокси. Окна запускаются из тестовой сборки Oblachka.exe. Настоящие ядра и VPN не запускаются,
внешних запросов нет. Принудительный GC и вытеснение страниц не используются.

Медианы трёх запусков, МиБ = 1024² байт:

| Фаза | Состояние имитации ядра | Приватная память владельца | Частный рабочий набор |
| --- | --- | ---: | ---: |
| До окон | Running | 16,03 | 10,89 |
| После закрытия первого окна | Running | 18,08 | 13,42 |
| После аварийного выхода второго | Running | 18,73 | 14,03 |
| После повторного открытия и закрытия | Running | 18,79 | 13,95 |
| После Stop из четвёртого окна | Idle | 18,85 | 14,40 |

PresentationFramework, PresentationCore и WindowsBase не загружены во владельце ни в одной
фазе ни одного запуска. Запись избранного сохраняется; явная остановка возвращает прежние
параметры имитируемого прокси. Сводка: `out/view-ipc-memory-20261102/summary.json`, исходные
отчёты — `ipc-{1,2,3}.json` и соответствующие отчёты дочерних окон в той же папке.

Эти числа относятся к владельцу с одним синтетическим профилем и ограниченным набором
функций. Они не являются замером полного клиента, установленного пользователем, и не
подтверждают результат «85 → 18,79 МБ» для него. Суммарная память при открытом основном
интерфейсе, реальные подключения, трафик и большие подписки ещё не измерены в новой схеме.

## Повторение

После `build.ps1` и `test.ps1`:

```powershell
dotnet build scripts/TrayProbe/TrayProbe.csproj -c Release -o out/tray-probe-ipc --configfile src/NuGet.Config -p:UseSharedCompilation=false
```

Запуск: `TrayProbe.exe --views <абсолютный путь out/test/Oblachka.exe> <абсолютный путь отчёта.json>`.
Только проверки IPC: `out/test/Oblachka.Tests.exe --view-channel-self-test <путь отчёта.json>`.

До включения нового режима остаются запуск подключения, выбор/импорт серверов, остальные
настройки и команды интерфейса, статистика, подписки, пауза VPN и наблюдение zapret. Их
нельзя заменить одним перенаправлением кнопки закрытия: это потеряло бы фоновые функции.

Полная проверка этапа: `build.ps1` без предупреждений; `test.ps1` — 380 логических и
62 интерфейсные проверки успешно. Поставляемая DLL проверена по 10 тестовым символам.
Имитация ядра в TrayProbe также проверяет, что Probe и Stop исполняются в исходном потоке
владельца с WinForms message loop, а не в потоке обслуживания канала.
