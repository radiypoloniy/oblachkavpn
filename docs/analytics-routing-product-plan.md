# Аналитика и маршрутизация как главные механики Облачков

Дата: 3 ноября 2026 года. Основа: код Windows-клиента на `1bf9868` (`v0.22.0-rc.9`).

Это продуктовый и технический план. Описанные ниже новые функции пока не реализованы. Оценки сложности относительные; сроки и ресурсные показатели требуют прототипа и замеров. Работающий VPN и его настройки при подготовке отчёта не менялись.

## 1. Предлагаемое направление

Сделать клиент инструментом понятного управления собственной сетью:

**Увидеть активность → понять причину маршрута → изменить правило → проверить результат → при необходимости отменить.**

Аналитика отвечает на вопросы «кто расходует трафик», «куда и каким путём идут соединения», «почему приложение не работает». Маршрутизация позволяет исправить ситуацию в том же контексте. Карточка программы, объяснение соединения и редактор правила должны работать с одной моделью данных.

Главные пользовательские результаты:

- Можно разобраться с одной проблемной программой без изучения JSON и сетевых терминов.
- Видно, какие исключения действительно используются и что именно выходит напрямую.
- Перед изменением понятны его масштаб и возможный разрыв соединений.
- После изменения есть проверяемый результат, а не только сообщение «Сохранено».
- Для этого не нужна постоянная запись истории посещений или расшифровка HTTPS.

| Диагностика | Проверка сайта через доступные разрешённые пути, этапы отказа, предложение правила | Связь с реальной программой, сценарий проверки после изменения |
| Короткая история программ | Память за последние 10 минут, выборка раз в 5 секунд, до 200 программ, без доменов | Понятный просмотр пользователем и обозначение неполноты |
| Приватность хранения | Локальное состояние зашифровано DPAPI для текущего пользователя Windows; в отчёте поддержки нет истории доменов | Раздельные разрешения на экспорт программ, путей и подробной диагностики |

В истории сейчас максимум 30 дней и 256 записей программ на день; интерфейс аналитики показывает только первые пять программ. Компактная сводка ядра также ограничена 256 группами. Избыточные данные агрегируются в «Другие программы».

Важно: нынешняя история **не содержит исторических байтов отдельно по VPN и прямому маршруту**. В журнале программ VPN/Direct/UDP — максимальные наблюдавшиеся количества соединений за выборку, а не объёмы трафика и не число всех соединений за период. Новые графики нельзя честно построить переименованием существующих полей.

### Границы текущих данных

- Основной исторический счётчик берёт данные ядра системного туннеля. Это не счётчик всего сетевого адаптера и не биллинг провайдера.
- В режиме прокси приложения могут обходить системный прокси. Таблицы Windows дают дополнительные сведения о соединениях, но сами по себе не доказывают прохождение через VPN.
- Периодическая выборка и ограниченное окно закрытых соединений могут пропускать очень короткую активность. Нужны отметки полноты, а для более точного учёта — события завершения соединений в ядре.
- Политика маршрутизации и наблюдённая цепочка выходов — разные сведения. Внешнюю доступность и внешний IP подтверждает отдельная активная проверка, которая сама создаёт сетевой трафик.
- Домен может быть неизвестен: приложение использует IP, собственный зашифрованный DNS или ECH. DoH защищает DNS-запросы от обычного сетевого просмотра, ECH шифрует ClientHello. Отсюда проектный вывод: честное «Имя не определено» предпочтительнее догадки по соседнему соединению или общему IP. [RFC 8484, раздел 10](https://www.rfc-editor.org/rfc/rfc8484.html#section-10), [RFC 9849](https://www.rfc-editor.org/rfc/rfc9849.html).

### Конкретные места, которые стоит исправить в начале

1. `RouteDecision.Of` сейчас получает путь программы и имя, а глобальные цели проверяет сравнением доменных суффиксов. При этом `SiteTarget` уже поддерживает IP/подсети и порты. Этот объяснитель используется также при выборе соединений для закрытия после изменения правил. Значит, до расширения интерфейса нужна проверка соответствия на этих типах целей и полный контекст соединения. По чтению кода виден разрыв моделей; конкретное поведение каждого случая следует закрепить воспроизводимыми тестами, а не объявлять всю маршрутизацию неисправной.
2. «Новый набор» сейчас меняет активные списки во время редактирования. Для ожидаемого поведения черновика нужна отдельная рабочая копия.
3. Группировка сайтов использует эвристику последних частей имени, а не PSL. Это ограничение группировки, не доказательство неверной работы всех доменных правил.
4. История содержит больше программ, чем пять строк текущего экрана. Полный список с поиском даст пользу раньше, чем новый сбор подробных данных.
5. Отчёт поддержки маскирует профиль пользователя в пути, но экспорт правил содержит исходные поля папок. У этих экспортов разные схемы приватности; нужен осознанный выбор состава обоих.

## 3. Какие сведения показывать пользователю

«Безопасно» здесь означает понятную цель, минимальный сбор и контроль пользователя. Даже список установленных программ, IP и объёмы по времени могут раскрывать привычки или рабочую инфраструктуру.

| Сведения | Отображение | Хранение и передача |
|---|---|---|
| Объёмы, скорость, приём/передача | Обзор и история по умолчанию | Локальные агрегаты, срок 30 дней как сейчас; без удалённой телеметрии |
| Программа и её расход | Полный список с поиском; путь раскрывается по действию | Локальные агрегаты; при экспорте по умолчанию имя файла, без личных папок |
| VPN/напрямую/блокировано/не определено | По наблюдаемым данным с отдельной пометкой для расчётного решения | В будущей истории — ограниченные агрегаты; попытки блокировки отдельно от переданных байтов |
| Адрес, порт, TCP/UDP, доступное имя | Подробности живого соединения | Без постоянной истории адресов по умолчанию |
| Причина решения и правило | В карточке соединения и программе | Идентификатор и версия правила, источник, результат применения; без обязательного доменного журнала |
| DNS | Доступные данные: источник имени, выбранный резолвер, результат, давность | Короткий локальный буфер; не обещать знание DNS внутри чужого DoH |
| Измерения серверов | Успешность, длительность теста, скорость, давность и сеть измерения | Локально; адреса серверов и ключи не включать в общий отчёт |
| События подключения | Подключение, восстановление, смена набора, ошибка применения | Коды и время в ограниченном журнале; без произвольного вывода ядра |
| Домены в истории и детальные события | Только отдельный режим подробной диагностики | Ограничение времени/объёма, отдельное сохранение и экспорт по выбору |
| Внешний IP, ASN, страна адреса | Дополнительные сведения по запросу | Не отправлять каждый адрес внешним справочникам; география приблизительная |

Предлагаю три режима:

1. **Обычный:** локальные агрегаты; живые подробности доступны при открытии экрана, но не превращаются в постоянную историю сайтов.
2. **Диагностика на 15 минут:** явный запуск с перечнем собираемых полей, ограниченный буфер, таймер и остановка. По умолчанию данные остаются в памяти. Сохранить выбранную сессию можно отдельно, зашифрованно, например на 7 дней с автоудалением.
3. **Поделиться отчётом:** предварительный просмотр и переключатели «состояние», «программы», «правила», «адреса». Последние категории не добавляются автоматически. Видно точное содержимое файла до передачи.

DPAPI защищает файл состояния, но не защищает от вредоносной программы, уже работающей от имени того же пользователя, и не делает экспорт анонимным. Текущий отчёт поддержки скрывает имя пользователя в пути, но название программы и оставшаяся папка тоже могут быть чувствительными. Экспорт правил сейчас может содержать полные пути: для него нужен собственный приватный/переносимый вариант.

Никакой установки корневого сертификата, перехвата cookies, ключей, содержимого сообщений или HTTPS-расшифровки ради аналитики. Полный URL страницы не требуется: для маршрутизации обычно достаточно доступного имени, адреса и контекста приложения. Иконки сайтов и обогащение адресов не должны незаметно запрашиваться у внешних сервисов.

## 4. Аналитика: предлагаемые улучшения

### A1. Обзор, который объясняет ситуацию

Первые карточки: приём/передача за выбранный период, текущая скорость, основные программы, действующий набор и состояние защиты. После появления новых счётчиков — доля наблюдённого трафика VPN/напрямую и отдельно нераспределённая часть.

Рядом всегда видны границы: «Системный туннель», «Только наблюдаемые соединения», «Обновлено 3 секунды назад». Пропущенные замеры не превращаем в нулевую скорость. Сравнение «сегодня/вчера» сопоставляет одинаковое прошедшее время, а не половину дня с полными сутками.

Клик по любой сумме ведёт к её составу. Нельзя показывать красивую диаграмму, если пользователь не может понять, откуда она взялась.

### A2. Полноценная карточка программы

Предлагаемый главный экран анализа:

- Название, файл, раскрываемый путь; при доступности — проверенные сведения о подписи. Подпись не означает безопасность программы.
- Трафик за период и график; живые скорости и соединения.
- Отдельно текущие наблюдаемые маршруты и назначенная политика: у одной программы они могут быть смешанными.
- Домены/IP текущих соединений с поиском и группировкой; неизвестные имена остаются неизвестными.
- Все относящиеся к программе правила, включая исключения по сайтам, и причина победы одного из них.
- Действия «Правило для программы», «Только для этого сайта», «Проверить», «Показать затронутые соединения».

Группировка «игра + лаунчер + вспомогательные процессы» должна показывать состав. Автоматически объединять всё из широкой папки вроде `Program Files` или всё с одинаковым `exe` опасно. Перенос программы в новую папку — повод подтвердить обновление области правила, а не молча расширить её.

### A3. «Почему это соединение идёт так?»

Карточка объяснения, например:

> `game.exe → voice.example.net:443 / UDP`
>
> Назначенная политика: VPN.
>
> Причина расчёта: правило «Голос игры», область — этот файл и этот домен.
>
> Ядро наблюдает: выход VPN, сервер группы «Игры».
>
> Правила версии 42 переданы; подтверждение применения доступно/пока ожидается.
>
> Имя получено из доступных метаданных соединения.

При наличии идентификатора реально сработавшего правила показываем его. Если ядро отдаёт только цепочку выходов, объяснение совпадения подписываем как расчёт по снимку политики. Для надёжной привязки нужны версия конфигурации на момент установления соединения и, где возможно, фактический идентификатор правила из ядра.

На другой вкладке — «Что победило и почему»: правило программы, доменное исключение, набор сервиса, встроенный список, маршрут по умолчанию. Это не свободный рассказ, а воспроизводимое объяснение приоритетов.

### A4. Полезная история без журнала посещений

Расширить существующую историю до измерений **дата × программа × класс маршрута**, сохранив приём/передачу и исходные ограничения размера. Дополнительные срезы по серверу или набору вводить с отдельным лимитом комбинаций, а не бесконечно перемножать измерения.

Пользователь сможет увидеть, какая программа расходовала VPN-трафик, сколько ушло напрямую, как менялся расход после смены набора. Из старых записей такой срез не восстановить: показать «Разделение маршрутов доступно с даты обновления». Время изменения правила — аннотация, а не доказательство, что оно вызвало изменение скорости.

Общие суммы ядра, суммы программ и нераспределённая часть показываются отдельно, если их охват отличается. Не подгонять их искусственно друг к другу.

### A5. События и локальные подсказки

Компактная лента: смена сервера, восстановление, переключение сети/набора, начало действия исключения, ошибка применения. Полезные подсказки должны иметь проверяемое основание:

- «Правило папки перекрывает правило этого сайта».
- «Для этих соединений имя не определено; доменное правило могло не совпасть».
- «Новое правило сохранено, но для прямого выхода требуется переподключение».
- «После изменения остаются старые соединения; проверить новые».

Для «правило не использовалось» нужна накопленная достаточная выборка; отсутствие попаданий при неполном наблюдении не доказывает бесполезность. Не вводить выдуманный процент безопасности, автоматические обвинения программ в слежке или рекомендации на основании одного всплеска трафика.

### A6. Проверка конкретной проблемы

Развить существующую проверку сайта в сценарий из карточки программы: цель → доступные проверяемые пути → DNS/установление соединения/TLS/HTTP → аккуратное объяснение → предложение узкого правила → проверка после применения.

У существующих эвристик вроде признаков блокировки должны быть формулировки «похоже», а не безусловный диагноз. Успех HTTP-проверки сайта не доказывает работу голосового UDP, авторизации или всего приложения. Для Discord/игры понадобятся отдельные сценарии проверки с известными ограничениями.

Прямой тест раскрывает адрес источника стороне назначения и может использовать DNS физической сети. Это активное действие пользователя с понятным описанием; если текущая защита не разрешает прямой путь, результат «Не проверялось» допустим. Нельзя незаметно ослаблять WFP ради сравнения.

### A7. Лимиты, избранное и сравнение серверов

Локальные пороги расхода: предупредить о выбранном объёме за день или месяц, отдельно по VPN после появления нужных счётчиков. Провайдерская квота показывается рядом с собственным источником и датой обновления, но не объединяется с локальной статистикой: объём, расчётный период и учитываемые устройства могут различаться. Автоматически блокировать или переводить трафик напрямую при достижении порога не нужно.

Избранные программы и сохранённые фильтры позволят быстро возвращаться к играм и рабочим приложениям. В сравнении серверов полезны успешность, давность теста, длительность установления проверочного соединения, измеренная скорость и история восстановлений. Длительность TCP/TLS-проверки не называть игровым пингом, разброс таких замеров — джиттером голосового потока, а неуспешные HTTP-запросы — потерей сетевых пакетов. Активное сравнение запускать по действию и в пределах понятного расхода трафика.

## 5. Маршрутизация: предлагаемые улучшения

### R1. Конструктор правил человеческим языком

Основная форма: **«Для [программы/группы] к [сайту/списку/подсети/любому адресу] использовать [VPN/напрямую/блокировать]»**.

По умолчанию показывать простые условия. Порт, TCP/UDP, семейство адресов, срок действия — в дополнительных параметрах. Домен точно и домен с поддоменами должны быть разными понятными вариантами; сейчас обычное доменное правило компилируется как суффикс.

Программа + домен уже поддерживается. Составные условия программа + подсеть/порт/протокол нужно расширять в модели и проверять для каждого движка. Документация sing-box содержит условия процесса, домена, IP, порта и логические правила, но это не означает одинаковую поддержку во всех используемых ядрах и режимах. Нужна явная матрица возможностей. [Route Rule](https://sing-box.sagernet.org/configuration/route/rule/).

При несовместимости не расширять условие до более общего и не притворяться, что оно действует. Показать ограничение и доступный вариант.

### R2. Предварительный просмотр до применения

Для будущего изменения показывать:

- Какие сохранённые правила изменятся и какие новые исключения появятся.
- Какие **сейчас наблюдаемые** соединения совпали бы с новой политикой. Будущий трафик и неизвестные имена сюда не входят.
- Какие правила будут перекрыты и почему.
- Что станет выходить напрямую и каким DNS-путём, если это известно.
- Потребуется ли переподключение, закрытие отдельных соединений или смена сервера.

Симуляция локальная и не создаёт проверочных запросов. Это расчёт политики, а не доказательство будущего сетевого результата.

Сейчас создание нового набора очищает активные списки и вызывает применение до нажатия «Сохранить». Предлагаю отдельную модель черновика: редактирование и отмена вообще не затрагивают действующие маршруты; сеть меняется только после «Применить».

### R3. Понятный приоритет и поиск конфликтов

В первом этапе сохранить действующий порядок и сделать его видимым. У каждого правила: область, источник, действие, причина приоритета, статус использования. Выделять дубликаты, частичные пересечения, более широкое правило папки и несовместимые действия.

Свободный drag-and-drop порядка можно добавить позже, когда компиляторы и объяснение одинаково понимают приоритет. Пользовательский порядок не должен обходить служебные правила DNS, защиту управляющих соединений и ограничения безопасности.

### R4. Версии, применение и откат

Разделить состояния: **изменено в черновике → сохранено → передано → применение подтверждено → наблюдается на новых соединениях**. Если надёжного подтверждения от движка нет, так и писать. Зелёная галочка сохранения не подтверждает сетевой маршрут.

Каждое применение получает версию и ограниченную историю изменений. Перед изменением сохраняется предыдущая валидная версия. Команда «Отменить изменение» восстанавливает правила и проверяет результат; если DNS, WFP или ядро восстановлены лишь частично, это отдельная видимая ошибка, а не «Успешно».

Нужно выбрать поведение для уже открытых соединений. Мягкое изменение можно применить к новым, показав оставшиеся старые. Для блокировки или ужесточения защиты старые несоответствующие соединения нужно завершать сразу. UDP-сессии и голос могут прерваться — это нужно сообщать до действия. Текущий код уже закрывает затронутые соединения при изменениях; улучшение — управляемая и объяснимая семантика, а не потеря этой защиты.

### R5. Временные исключения

«До закрытия программы», «На 30 минут», «До отключения VPN» с постоянно видимым сроком. Временное прямое исключение — явное действие пользователя с такой же областью и проверкой, как постоянное.

По истечении срока вернуть прежнюю политику и закрыть соединения, которые нарушают восстановленное ограничение. Перезапуск и сон компьютера не должны случайно продлевать разрешение. При неоднозначном состоянии исключение не включается заново без подтверждённых данных о сроке.

### R6. Группы программ и сервисов

Два разных объекта: пользовательская группа файлов/папок и версионируемый набор доменов/IP сервиса. Например, «Моя игра» и «Голос Discord» — не одно и то же.

У шаблона видны состав, назначение, источник, дата и ограничения покрытия. Общие CDN не следует целиком выводить напрямую ради одного сервиса. Нужны включение/исключение отдельных элементов и просмотр изменений обновления. Шаблон может предложить правила, но не должен незаметно переводить существующий VPN-трафик в Direct.

Импорт уже есть. Следующее улучшение — просмотр diff, отключённые до проверки неизвестные пути, переносимые ссылки на выбранные пользователем приложения и отдельное подтверждение расширения прямых исключений. Внешний набор — только типизированные данные с ограничениями размера/сложности, без команд и произвольного кода. Подпись источника подтверждает происхождение, а не безвредность содержания.

### R7. Наборы по сети и ручное переопределение

Привязка набора к сети уже реализована. Развивать её стоит через видимое объяснение «Включён “Работа”, потому что сеть …», предварительный просмотр различий и ручное переопределение до следующего согласованного события.

Защита от колебаний сети: объединять частые изменения, не переключать набор туда-обратно на кратких событиях интерфейса. Имя Wi-Fi само по себе не является доказательством доверия; текущий идентификатор сети Windows тоже не следует представлять как криптографическую идентичность точки доступа. Смена сети не должна автоматически выключать уже работающий VPN.

### R8. DNS как часть политики

В карточке правила показывать доступное объяснение: куда должен идти трафик и где разрешается имя. Возможные различия — системный DNS, DNS через VPN, DNS прямого исключения, собственный DoH приложения.

Перед расширением правил по приложениям отдельно исследовать DNS для одного домена, одновременно используемого разными программами с разными маршрутами. Общие кэши и запросы вне видимости ядра мешают обещать строгую изоляцию «DNS каждой программы». Нужны тесты выбранной схемы, отсутствие небезопасного fallback и честная маркировка неизвестного. Сам факт DoH не означает корректность ответа или правильный выбор маршрута. [RFC 8484, разделы 9–10](https://www.rfc-editor.org/rfc/rfc8484.html#section-9).

### R9. Отдельные серверы/группы для разных программ

Самая заметная продвинутая функция: браузер — группа «Обычная», игра — «Низкая задержка», рабочая программа — фиксированный сервер. Резервный сервер выбирается **внутри разрешённой VPN-группы**, без автоматического перехода в Direct при отказе.

Сейчас ограничение серверов относится к набору целиком; независимого выбора для каждой программы в существующей модели нет. Потребуются несколько логических групп выходов, стабильные идентификаторы, проверка совместимости транспортов, DNS-политики и предварительная авторизация пиров в сетевой службе. Примитив selector у sing-box есть, но безопасная интеграция в клиент — отдельный этап. [Selector](https://sing-box.sagernet.org/configuration/outbound/selector/).

Группы должны использовать одно ядро там, где это поддерживается, и не запускать отдельный процесс на каждое приложение. Для неподдерживаемых транспортов нужен ограниченный и явно описанный вариант, а не скрытый рост числа ядер.

#### Первый этап строгой привязки

Сохранённое правило содержит домены, точные пути к исполняемым файлам и стабильный идентификатор профиля сервера. При запуске системного туннеля клиент выделяет места для таких профилей перед обычными запасными. Сетевая служба проверяет, что каждый закреплённый выход входит в текущую аренду и ведёт к разрешённому пиру. Основной сервер и закреплённые выходы работают в одном ядре.

Если профиль отсутствует, отфильтрован или его транспорт нельзя встроить в ядро, совпавшее соединение отклоняется. При сетевом отказе совпавшее соединение остаётся на закреплённом выходе и завершается ошибкой. Смена основного сервера через селектор сама по себе не меняет закрепления. Привязки пересчитываются при создании аренды.

Системные ограничения и явные правила пользователя проверяются раньше правил сервисов. Списки и основной маршрут проверяются после них. Внутри правил сервисов точный путь проверяется раньше домена, а более конкретный домен раньше общего. Перед открытием настройки нужно показывать конфликты с явными правилами, которые могут перехватить трафик сервиса.

До выпуска нужны проверенные наборы доменов и программ для Claude и ChatGPT, состояние каждого закрепления и проверка связи именно через его выход. Уведомление должно различать отсутствующий профиль, неподдерживаемый транспорт и потерю связи. Общая кнопка управляет системным туннелем. Отказ закреплённого выхода меняет состояние его маршрута. На Windows-стенде отдельно проверяются DNS, защита WFP, смена сети и восстановление после отказа основного сервера.

### R10. Понятные режимы без ложных обещаний

Развить существующие режимы «всё через VPN» и «только выбранное» готовыми стартовыми сценариями: игры, работа, доступ к отдельным сервисам. Перед включением — список затрагиваемых приложений, прямых исключений и локальной сети.

Обход DPI через zapret обозначать как **прямой выход с обходом DPI**, а не отдельный вид VPN-шифрования. Проверка доступности сервиса, наличие TLS и защита всего системного трафика — разные свойства интерфейса.

## 6. Как сделать это приятным

Предлагаю три основных места с единым поиском и переходами:

1. **Активность:** обзор, список программ, раскрываемая карточка и текущие соединения.
2. **Правила:** наборы, поиск, понятный конструктор, предпросмотр, версии и отмена.
3. **Проверка:** запуск из конкретной программы/соединения, последовательность этапов, предложенное изменение и повторная проверка.

Исторические графики доступны из «Активности» и карточки программы. Не требуется держать все подробности одновременно на главной странице.

Общие требования:

- Один и тот же выбор программы, периода и набора сохраняется при переходе между связанными экранами.
- Простой вид по умолчанию; технические поля раскрываются без отдельного «режима эксперта», который нужно искать.
- Различать «неизвестно», «нет данных», «не проверялось», «нулевой трафик» и «заблокировано».
- Цвет подкреплён подписью и значком; клавиатура, экранный диктор, светлая/тёмная тема, узкое окно.
- В живом списке — пауза обновления, чтобы строки не уезжали из-под курсора; обновления накапливаются ограниченно.
- Массовые действия только с видимой областью; после операции — точный результат и доступная отмена.
- Короткие уведомления по существенной проблеме применения, без уведомления на каждое соединение.

### Пример законченного сценария

Пользователь открывает игру в «Активности» → видит лаунчер и голосовые соединения → открывает «Почему этот маршрут?» → замечает широкое правило папки → создаёт узкое исключение для голосового домена → видит, что затронутся два текущих соединения → применяет → клиент подтверждает передачу политики и показывает наблюдение новых соединений → пользователь проверяет голос → при проблеме отменяет ровно это изменение.

Именно такую целую цепочку стоит выпустить первой. Она даст больше заметной пользы, чем десяток дополнительных графиков без связи с действиями.

## 7. Техническая основа и цена по ресурсам

### Единая модель решения

Вместо нескольких независимых догадок интерфейса — типизированная политика со стабильными ID правила/набора/группы выхода, происхождением, версией и описанием условий. Из неё строятся конфигурации поддерживаемых ядер и локальный объяснитель. Одинаковая модель уменьшает расхождения, но не заменяет проверки реально скомпилированных конфигураций.

Нужны тесты соответствия для доменов, IP, портов, правил программы и их приоритетов. Снимок правил должен соответствовать моменту создания соединения: сегодняшняя политика не объясняет автоматически вчерашнее решение. При нехватке данных выводится ограничение, а не придуманный ID правила.

### События и агрегаты

Текущий экономичный компактный опрос сохраняется как базовый механизм. Для точных событий завершения/отклонения соединений исследовать адаптер внутри ядра: ограниченные счётчики и очередь, без обработки каждого пакета в GUI. При невозможности полного учёта оставлять выборку и показывать её ограничения.

Канал событий должен иметь последовательность, эпоху ядра и счётчик потерь. Тогда перезапуск, сброс статистики или переполнение не создают огромных ложных дельт. Очередь ограничена; переполнение агрегирует данные и отмечает пропуск. Сервер событий не должен блокировать сетевой тракт из-за медленного интерфейса.

Фоновая история хранит агрегаты без адресов; подробности загружаются по запросу. Для новых версий формата нужны миграция, сохранение старых сумм и тесты границ периода. Программа без определённого владельца попадает в отдельную группу, а не приписывается соседнему процессу.

### Ограничения роста

- Оставить 30 дней стандартной истории; увеличение периода — отдельная настройка и расчёт размера.
- Лимитировать не только программы, но и число комбинаций программа/маршрут/набор. Переполнение — явная группа «Другие».
- Для диагностического буфера начать с ограничения по времени и двойного предела, например 2 000 событий **и** 4 МиБ сериализованных данных; фактическая память будет больше и измеряется отдельно. Это стартовые проектные пределы, не текущая реализация.
- Не создавать по объекту UI на каждое соединение; виртуализация, постраничные запросы, изменения строк вместо перестроения всей страницы.
- Закрытый экран не обновляет графики и не запрашивает полную таблицу соединений. В трее остаётся только необходимый сбор агрегатов.
- DNS-справочники, география и доменные списки не сканируются целиком на каждый тик. Справочники обновляются независимо, с фиксированным размером кэша.
- Не делать активные скоростные/доступностные тесты для каждого обнаруженного домена. Пассивная аналитика и явная диагностика — разные режимы.

Первые измеримые критерии: ограниченный размер состояния и очередей, отсутствие растущей памяти на длительном прогоне, отсутствие новых постоянных полных опросов в трее. Сравнить CPU, private bytes, private working set, сборки GC и задержку UI с выключенными/включёнными функциями на одной нагрузке. Для сетевого тракта — пропускная способность и задержка на одинаковом стенде. Допустимый численный бюджет определить после прототипа; обещать заранее «почти бесплатно» было бы неверно.

### Обязательные границы безопасности

- Новая аналитика не расширяет разрешения WFP и не снимает блокировку обхода VPN.
- Новый прямой выход — только следствие явной политики пользователя; недоступность VPN не превращается в Direct.
- Пиры, локальные управляющие входы и DNS согласуются с допустимой конфигурацией сетевой службы. При необходимости переподключения это видно до применения.
- Управление остаётся локальным и аутентифицированным; не открывать контроллер в LAN и не добавлять внешний веб-интерфейс ради диаграмм. Clash API предусматривает адрес слушателя и секрет, а текущие проверки локального владельца порта необходимо сохранить. [Clash API](https://sing-box.sagernet.org/configuration/experimental/clash-api/).
- Импорт/обновление списков ограничивает размер, сложность, типы полей и доступные действия; предыдущая рабочая версия остаётся для отката.
- Защитные системные правила не редактируются как обычные пользовательские исключения. Частично применённое состояние отображается отдельно.

В текущем коде есть эвристика группировки имени по двум/трём последним частям домена. Для отображения нужна корректная группировка по Public Suffix List, включая соответствующий учёт частных суффиксов. Группа отображения не должна автоматически становиться широким правилом; исходное имя сохраняется и область выбирается явно. PSL предназначен в том числе для такой группировки, но не является списком всех валидных доменов. [Пояснение проекта PSL](https://publicsuffix.org/learn/).

## 8. Приоритеты

Сложность: S — небольшой самостоятельный шаг; M — несколько связанных частей; L — модель данных/ядро/служба и существенная проверка. Это относительная оценка, не обещание срока.

| Улучшение | Пользовательская польза | Приоритет | Сложность |
|---|---|---|---|
| Источник, свежесть и полнота данных | Устраняет ложные выводы из статистики | P0 | M |
| Состояния сохранения/передачи/применения | Понятно, почему правило пока не работает | P0 | M |
| Единые ID, версии и семантика правил | Основа объяснения, истории и отката | P0 | L |
| Карточка программы с полным списком | Видимый шаг от пяти строк к анализу | P1 | M |
| «Почему выбран этот маршрут?» | Главная отличительная механика | P1 | M–L |
| Конструктор и предпросмотр | Безопасное изменение без знания конфигов | P1 | L |
| Настоящий черновик и отмена изменения | Редактирование без неожиданной смены сети | P1 | M–L |

### Порядок выпуска

**Этап 1 — доверие и одна законченная механика.** Подготовить минимальную общую модель, показать источник/давность, сделать карточку программы и объяснение, затем узкий конструктор с предпросмотром, настоящим черновиком и отменой. Первый пользовательский сценарий — исправление маршрута одной программы и проверка результата.

**Этап 2 — аналитика, полезная каждый день.** Добавить агрегаты по маршрутам, полную историю программы, сравнение периодов, ленту событий, приватный экспорт и связанную диагностику. Не пытаться восстановить отсутствующие измерения старых данных.

**Этап 3 — удобная сложная политика.** Временные правила, группы, шаблоны, улучшенные привязки к сетям и DNS-объяснение. Обновления шаблонов с просмотром изменений и отдельным контролем прямого выхода.

**Этап 4 — разные VPN-группы одновременно.** Сначала исследовательский прототип с проверкой транспортов, DNS и WFP, затем пользовательская настройка. Это отдельная большая функция, а не маленькая доработка списка серверов.

Не начинал бы с постоянной карты мира, автоматического определения «опасных программ», бессрочной истории доменов, отправки трафика облачному ИИ, универсального QoS или заявления «видим всё». Они добавят стоимость, риски и сопровождение раньше, чем решат основной пользовательский сценарий. Ограничение скорости по программам, например, требует отдельного механизма управления трафиком: наличие правила маршрута не даёт такой функции автоматически.

## 9. Как проверять результат

Приёмка по пользовательским задачам:

1. Для доступного наблюдению соединения можно открыть программу, объяснение и относящееся правило из одного места; неизвестные данные явно обозначены.
2. Отмена черновика не меняет действующий набор и не разрывает соединения.
3. Предпросмотр и исполнение совпадают на поддерживаемых условиях. Неподдерживаемое сочетание не превращается в более широкое правило.
4. После изменения видно отдельно состояние политики и новых соединений. При частичном отказе нет ложного сообщения об успехе.
5. Временное исключение корректно истекает после сна и перезапуска; ужесточённая политика не оставляет старый прямой выход.
6. По умолчанию на диске не возникает история доменов. Экспорт содержит только поля, выбранные на предварительном просмотре.
7. При отказе VPN, смене сети, DNS и обновлении набора нет автоматического обхода защиты; активные проверки не расширяют разрешения.
8. Большое количество коротких соединений, программ и обновлений списка не вызывает неограниченный рост памяти. Пропуски наблюдения отражаются в данных.

Пограничные проверки: одинаковые имена `exe` в разных папках; папка и вложенный файл; IDN и суффиксы доменов; IPv4/IPv6; общие IP CDN; собственный DoH и ECH; сон/полночь/смена часового пояса; перезапуск ядра и сброс статистики; потеря событий; старые TCP и UDP после изменения; сбой одного шага применения и отката; переход между TUN и прокси; несовместимые транспорты и недоступный сервер группы.

Для оценки удобства фиксировать в ручных тестах время до нахождения причины и число шагов до корректного правила. Не добавлять продуктовую удалённую телеметрию ради этих метрик.
