# Блокировка трафика мимо туннеля на VM · 13 октября 2026

Стенд тот же, что в [прогонах 12 октября](VM-TUN-RESULTS-2026-10-12.md): VirtualBox, VM `VPNTests`, NAT, захват `nictrace` снаружи гостя. Прогон — `Oblachka.Tests.exe --system-tunnel-check` из задачи с правами администратора, весь путь окна: помощник, sing-box TUN, брандмауэр.

## Утренние прогоны были на нерабочем узле

Восемь утренних прогонов с блокировкой показывали «имя не разрешено» и отказ всех запросов, а проверка при этом писала «перенаправление подтверждено»: отказ сравнивался с исходным адресом как «другой выход». Вывод исправлен — ошибка теперь означает «связи нет».

Причина отказа была не в блокировке. Проверка разделена на три пути: без DNS (`1.1.1.1`), через локальный SOCKS ядра и обычный по имени. Узел «Авто» (TCP/REALITY, `5.252.155.19:443`) не работает ни одним путём, **и с выключенным брандмауэром тоже**: в захвате 164 соединения с узлом, в каждом около 3 КБ туда и 5 КБ обратно, затем закрытие. Это вопрос к узлу или пути до него, не к клиенту. Отдельно проверить на сервере.

## Узел «Германия», XHTTP/REALITY, блокировка включена

| что | результат |
|---|---|
| имя через DNS туннеля | разрешено |
| запрос без DNS, по адресу | выход `103.227.84.243` |
| SOCKS ядра → узел | работает, ~300 мс |
| выход системы | `142.228.52.110` → `103.227.84.243`, два источника совпали |
| соединение, открытое до включения | оборвано блокировкой |
| остановка | брандмауэр вернул Allow, наших правил 0, выход прежний |

В захвате внутри окна туннеля мимо узла **0 кадров и 0 новых соединений**. Повторено трижды.

**Смерть ядра.** Процесс ядра завершается снаружи. Сессия переходит в удержание, блокировка остаётся (`Block`, 7 правил), запрос при мёртвом ядре не проходит. В интервале захвата, пока ядро мертво, наружу не ушло ни одного кадра. Перезапуск занимает прежний локальный порт, интерфейс туннеля прежний, выход снова `103.227.84.243`.

**Разрешение узла только ядрам.** `curl` из Windows к адресу узла без своего правила не соединяется (код 7). Адрес узла выведен из туннеля маршрутом, так что раньше к нему мог выйти кто угодно.

**Чужое разрешение сильнее блокировки.** С разрешающим правилом для `curl` то же соединение проходит. В госте 122 включённых чужих разрешения для исходящего трафика, все привязаны к программе, службе или пакету; на хосте владельца 142. Внутри работающего туннеля это не важно — всё идёт маршрутом в туннель. Важно там, где туннеля нет, а блокировка стоит: адрес узла и края окна (запуск, остановка, восстановление помощником). Строгий режим брандмауэром Windows не обеспечить; для него нужен WFP с собственным подслоем.

## Края окна: аудит WFP

По захвату снаружи нельзя было решить, ушло ли соединение на остановке до снятия блокировки. Метки-SYN не помогли: часы гостя под VirtualBox за 70 с разошлись с часами захвата на 4,5 с. Решение — по часам самого гостя. Помощник пишет время каждого шага (`helper-trace.txt`: вид изменения и момент, без адресов), а аудит WFP (`vm-kit/wfp-audit.ps1`) записывает каждое исходящее соединение с программой, адресом и номером решившего фильтра.

Прогон на узле «Германия»:

| окно | длительность | исходящих соединений |
|---|---|---|
| блокировка встала, туннеля ещё нет | 2,9 с | 0 |
| туннель снят, блокировка в журнале ещё не снята | 2,9 с | 4, все `svchost` |

Эти четыре разрешены фильтром «исходящее по умолчанию разрешено» (тот же номер через 0,2 с у `xray` и `svchost`, уже после снятия). Пока блокировка стоит, отказ идёт её фильтром: так отклонены `curl` к узлу и ранее открытое соединение. Значит, к моменту этих соединений исходящее действие уже было возвращено, а отметка журнала пишется после снятия и правил. Снятие идёт в задуманном порядке: туннель, затем блокировка, и ничего не выходит мимо, пока блокировка действует.

Первый запрос подписки из задачи с правами сразу после смены DNS гостя падает, второй проходит. Проверка теперь делает до трёх попыток.

## Защита фильтрами WFP

Блокировка перенесена с брандмауэра на Windows Filtering Platform (`WfpProtectionBackend`): собственный подслой с наибольшим весом на слоях `ALE_AUTH_CONNECT` IPv4 и IPv6. Разрешены loopback, трафик с адреса туннеля, резолвер туннеля, `xray.exe`/`sing-box.exe` сборки к адресам узлов и DHCP; остальное — запрет. Брандмауэр Windows больше не меняется; он остаётся запасной защитой, если служба фильтрации недоступна.

| проверка | брандмауэр вкл | брандмауэр выкл |
|---|---|---|
| фильтров при поднятом режиме | 12, слои и условия Windows называет своими именами — ключи верны | 12 |
| туннель, DNS, выход `103.227.84.243` | да | да |
| соединение, открытое до включения | оборвано | оборвано |
| `curl` к узлу без правила | не соединился | не соединился |
| `curl` к узлу **с собственным разрешением** | **не соединился** (раньше соединялся) | не соединился |
| смерть ядра | удержание, восстановление | удержание, восстановление |
| фильтров после остановки | 0 | 0 |

Захват снаружи: внутри окна мимо узла 0 новых соединений. В прогоне без брандмауэра один кадр мимо узла — RST нашего стека в ответ на FIN сервера по соединению, открытому до включения; данных в нём нет. Аудит WFP: пока защита стоит без туннеля (1,6 с на запуске, 13 мс на снятии), исходящих соединений 0. Защита снимается через 13 мс после туннеля, а не через 2,9 с, как правила брандмауэра.

**Смерть помощника.** Фильтры не динамические и переживают процесс: после завершения помощника 12 фильтров на месте, запрос без туннеля не проходит, журнал в `Applied`. Новый запуск помощника восстанавливает сеть по журналу: журнал `Released`, фильтров 0, выход прежний. Окно при запуске читает журнал и, если сессия не снята, предлагает «Восстановить сеть» — тот же запуск помощника. После перезагрузки фильтров нет: флаг постоянства не ставится.

## Совместимость под защитой WFP

| сценарий | результат |
|---|---|
| 20 минут непрерывно, замер каждые 15 с | 78 из 80 успешны, медиана 297 мс |
| обрыв линка на 30 с посреди сессии | провал 19 с, связь вернулась сама, без перезапуска ядра и туннеля; мимо узла 0 кадров |
| смена адаптера посреди сессии (второй NAT-адаптер, другая подсеть и шлюз) | 20 из 20 замеров успешны, провала нет; трафик к узлу перешёл на новый адаптер с адресом `10.0.3.15`; мимо узла 0 кадров |

**Hysteria2 на стенде не проверяется.** Узел `2.26.26.133:443` не отвечает и без защиты, и без туннеля: локальный SOCKS ядра не работает ни из гостя, ни с хоста. То же у TCP/REALITY `5.252.155.19:443`. Работает только XHTTP `5.252.155.19:2053`. Путь хоста идёт через его собственный VPN; вопрос к узлам или к этому пути, не к клиенту.

**IPv6 на стенде не проверяется.** У гостя только локальные адреса `fd17:…`, публичного выхода по IPv6 нет, `api6.ipify.org` недоступен и без туннеля. Проверка теперь замеряет IPv6 до туннеля и во время и кричит, если при поднятом туннеле виден собственный IPv6 машины, — но смысл это имеет только в сети с настоящим IPv6.

**Пакеты с адресом туннеля на физическом адаптере — закрыто.** На снятии туннеля соединения, жившие в нём, закрывались, и их FIN-ACK без данных уходили на физический адаптер с отправителем `172.31.255.1`: слой соединений пакеты уже разрешённых потоков не видит. Добавлен фильтр на слое исходящих IP-пакетов: адрес туннеля в отправителе и интерфейс не типа 53 (wintun, проверено на стенде) — запрет. Детерминированный опыт: UDP с сокета, привязанного к адресу туннеля, на адрес узла (он выведен из туннеля маршрутом и уходит физически). С фильтром в захвате 0 из 5 пакетов, в контрольной сборке без фильтра — 5 из 5.

## Открыто

- Интерфейсы `Obl-*` прошлых сессий копятся в системе (сейчас десять). Новой сессии не мешают, но это мусор.
- Завершение окна снимает сессию помощником — граница до появления службы.
- Кнопка «Восстановить сеть» проверена тем же запуском помощника из проверки стенда, но не нажатием в окне.
- Фильтры стоят на установлении соединений; входящие соединения из физической сети защита не ограничивает.
- Hysteria2, IPv6 и конфликт с другим VPN — только на реальной машине или сети: стенд их честно не воспроизводит.
