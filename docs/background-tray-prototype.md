# Фоновый владелец без WPF: измеренный прототип

Дата: 2 ноября 2026 года. Целевой пользовательский показатель — память отдельного
`Oblachka.exe` в трее (около 85 МБ), а не сумма процессов вместе с сетевыми ядрами.

## Что проверено

Отдельный `TrayProbe.exe` использует настоящие `ClientRuntime`, `ClientTray`,
`ClientHealthMonitor`, `ClientPersistence` и `ClientProxy` из поставляемой сборки клиента.
Он запускает WinForms message loop и NotifyIcon, создаёт один синтетический профиль,
проверяет связь через имитацию ядра, сохраняет избранное в отдельный зашифрованный файл
и исправляет подмену настроек имитируемого прокси. Настоящие ядра и TUN не запускаются,
настройки Windows и установленного клиента не меняются, внешних запросов нет.

До изменения `AppIcon.Small()` обращался к WPF `Application.GetResourceStream` через
pack URI. Без инициализации WPF этот путь завершался UriFormatException. Теперь трей
читает manifest resource того же `app.ico`; полученный Icon клонируется и не зависит от
времени жизни потока. WPF-ресурс для иконки самого окна сохранён.

Контрольный запуск использует прежнюю сборку клиента и создаёт WPF Application для
старого пути значка. Новый запуск не создаёт WPF Application. Стенд включает тот же
файл иконки как WPF-ресурс entry assembly для корректной работы старого pack URI.
Размер иконки и наличие нового manifest resource проверяются. Каждый процесс живёт
18 секунд; состояние меняется на пятой секунде. Принудительный GC и вытеснение страниц
не используются. Замеры идут последовательно, три пары, после завершения основных тестов.

## Результат

Медианы трёх парных запусков, МиБ = 1024² байт:

| Показатель | Фоновый владелец со старым WPF-путём значка | Фоновый владелец без WPF |
| --- | ---: | ---: |
| Приватная память процесса | 19,75 | 16,58 |
| Частный рабочий набор | 12,72 | 11,48 |
| Полный рабочий набор | 75,50 | 65,67 |
| Управляемая память | 3,26 | 3,07 |

В новых процессах не загружены PresentationFramework, PresentationCore и WindowsBase.
Во всех шести процессах проверены монитор связи, зашифрованная запись состояния,
исправление имитируемого прокси и живой трей. Данные и список загруженных сборок:
`out/background-tray-20261102/{before,after}-{1,2,3}.json`, сводка — `summary.json`.

Это уменьшение памяти фонового стенда, а не полноценного клиента с открывавшимся окном.
Рабочий клиент всё ещё создаёт MainWindow, поэтому замена источника значка сама по себе
не превращает его пользовательские 85 МБ в 16,58 МиБ. Прежний замер скрытого окна около
80 МиБ относится к другому сценарию — [стенду окна](tray-memory-baseline.md).

Прототип не включает реальный трафик, большой набор профилей, работу подписок, все фоновые
задачи zapret и IPC с отдельным процессом интерфейса. Его расход нельзя выдавать за
прогноз окончательного фонового клиента. Запуск отдельного окна также увеличит суммарный
расход во время работы интерфейса; этот режим ещё не измерен.

## Сопутствующее исправление

Повторные запуски обнаружили задержку стражника прокси: раннее срабатывание Timer
откладывало проверку ещё на пять секунд. Теперь назначается оставшийся интервал с нижним
ограничением 1 мс. Проверка с управляемыми часами подтверждает, что после раннего вызова
подмена исправляется до истечения двух секунд; прежний алгоритм назначал пять секунд.
Это исправление работоспособности таймера, оно не считается экономией RAM.

## Воспроизведение

Стенд собирается отдельно и ссылается на готовую production DLL из `out/app`:

```powershell
.\build.ps1
dotnet build scripts/TrayProbe/TrayProbe.csproj -c Release -o out/tray-probe --configfile src/NuGet.Config -p:UseSharedCompilation=false
```

Запуск нового варианта: `TrayProbe.exe <абсолютный путь отчёта.json>`.
Контроль WPF-инициализации: `TrayProbe.exe --wpf-baseline <путь отчёта.json>`.
Для точного сравнения старой и новой загрузки значка сначала нужно собрать и сохранить
стенд с production DLL до изменения AppIcon (исходники на коммите `5bc0463`), затем
собрать новый вариант. `scripts/TrayProbe/Compare.ps1` принимает `-Before`, `-After` и
`-OutputFolder`, запускает три пары и сохраняет медианы. Оба стенда должны использовать
одинаковую версию TrayProbe; клиентские DLL должны оставаться соответствующих версий.

Проверка рабочего изменения: `build.ps1` без предупреждений; `test.ps1` — 371 логическая
и 62 интерфейсные проверки успешно. Поставляемая сборка без тестового кода.

## Следующий рубеж

Перед выпуском режима с меньшей памятью в трее нужны передача состояния и команд между
владельцем подключения и процессом окна, перенос оставшихся операций из MainWindow и
проверки закрытия/повторного открытия интерфейса с сохранением настоящего подключения.
Критерий приёмки — замер памяти после открытия, закрытия и повторного открытия окна,
с реальным трафиком и всеми фоновыми функциями. Сам по себе запуск этого стенда не
включает новый режим в установленном приложении.
