# Оптимизация памяти — 1 ноября 2026

Первый этап сохраняет сетевые протоколы, правила, проверки TLS, WFP, защиту DNS,
восстановление сессии и частоту фонового учёта. Работающая установленная копия
не заменялась; реальные подключения при замерах не переключались.

## Изменения

- Аналитика, выбор программ, диагностика сети и проверка сайта создаются при
  первом открытии. Повторное открытие сохраняет экземпляр, состояние и обработчики.
  Остальные страницы пока остаются в дереве: их контролы используются как модель настроек.
- Список программ виртуализирован с переиспользованием контейнеров. Каталог больше
  не извлекает все значки заранее. Значки запрашиваются при показе в фоне (до четырёх задач); кэш ограничен 256
  записями. Выбор, поиск и доступность кнопок через визуальное дерево сохранены.
- Неактуальные строки сайтов и программ удаляются из кэшей. Заблокированные
  программы остаются доступными для снятия правила. История трафика не сокращается.
- Фоновый учёт программ и экран соединений разделяют один выполняющийся запрос
  и снимки не старше 250 мс. Отмена одного потребителя не отменяет другой запрос;
  при смене сессии снимок сбрасывается. Запоздавшие ответы старой сессии игнорируются.
- Команды закрытия соединений и применения правил читают свежие данные напрямую,
  минуя кэш. Авторизация локального API и тайм-аут сохранены.
- HTTP-ответ соединений разбирается из потока в `JsonDocument`, без промежуточной
  UTF-16 строки и изменяемого дерева `JsonNode`. Короткие сообщения скорости также
  используют `JsonDocument`.
- Карточки подписок перерисовываются при изменении группы, данных, операции,
  настроек сохранения и временного порога; состояние обновляется в том числе в
  точный момент истечения. Сетевые проверки и уведомления продолжают опрашиваться.

## Методика и результаты

Медианы трёх парных запусков «до/после» на одной машине. UI-стенд выполняет
конструктор и раскладку окна без его показа, затем загружает синтетические
профили и открывает аналитику. Сетевые ядра и реальные подписки не используются.
Принудительный GC и очистка рабочего набора отсутствуют.

| Показатель | До | После |
| --- | ---: | ---: |
| Приватная память, старт | 49,44 МиБ | 49,46 МиБ |
| Приватная память, главный экран | 62,41 МиБ | 59,56 МиБ |
| Приватная память, аналитика | 62,94 МиБ | 60,11 МиБ |
| Рабочий набор, главный экран | 135,83 МиБ | 132,39 МиБ |
| Выделения за 100 обновлений главного экрана | 1,66 МиБ | 1,54 МиБ |

Это небольшой выигрыш постоянной памяти окна, а не достижение 18 МиБ для всего
клиента. Стенд не измеряет TUN, службу, реальный трафик, GPU-ресурсы показанного
окна и длительную сессию. Размер управляемой кучи без GC может включать мусор;
его нельзя выдавать за размер только живых объектов.

Отдельный тест разбора одинакового ответа из 2000 соединений: пять прогревочных
вызовов, затем 30 вызовов, по три отдельных процесса на каждую сборку.

| Показатель | До | После |
| --- | ---: | ---: |
| Суммарные выделения памяти | 191,27 МиБ | 36,63 МиБ |
| Время 30 разборов | 635,7 мс | 467,4 мс |

Выделения сократились на 80,8%, время на этом стенде — на 26,5%.
Это временные выделения, а не уменьшение постоянно занятой ОЗУ на 155 МиБ.

## Повторение

Сохраните исходную тестовую сборку отдельно перед изменениями. Для обеих версий
используйте Release и одинаковый `IncludeTestCode=true`.

```powershell
dotnet build tests/Oblachka.Tests.csproj -c Release -o out/memory-after --configfile src/NuGet.Config -p:IncludeTestCode=true -p:UseSharedCompilation=false
out/memory-after/Oblachka.exe --ui-memory-check out/memory-after/sample.json

dotnet build scripts/MemoryProbe/MemoryProbe.csproj -c Release -o out/memory-probe --configfile src/NuGet.Config
out/memory-probe/MemoryProbe.exe out/memory-before/Oblachka.dll out/memory-before/parser.json
out/memory-probe/MemoryProbe.exe out/memory-after/Oblachka.dll out/memory-after/parser.json

.\test.ps1
```

Замеры выполняйте последовательно, без одновременного запуска полного набора
тестов. UI-команда и стенд отсутствуют в обычной поставляемой сборке.

## Более крупные следующие этапы

Отдельный Xray нельзя просто убрать во всех режимах: фрагментация, неподдерживаемые
параметры, совместимость со службой и пути прямого трафика должны сохранить поведение.
Путь с одним ядром уже существует; расширять его следует с интеграционными проверками
на изолированном TUN-стенде. Защитные условия в этом изменении не ослаблялись.

Отделение фонового контроллера и службы от WPF — отдельная архитектурная работа.
Она может дать больший постоянный выигрыш, чем изменения четырёх экранов, но
потребует сохранения проверки владельца IPC, heartbeat и поведения при аварии.
