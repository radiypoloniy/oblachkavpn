# CPU полного окна и ядра — 2 ноября 2026

База клиента: 9c39f08. Цель этапа — измерить работу процесса во времени,
снять профили и убрать подтверждённую лишнюю работу. Установленная копия,
служба, маршруты и действующая VPN-сессия не заменялись.

## Изменения

1. Число серверов на главной берётся из существующего индекса машин. Раньше
   каждое обновление главной заново группировало до 600 профилей, создавало
   массивы групп и затем выбрасывало их. Индекс обновляется при замене списка;
   несколько протоколов одного адреса по-прежнему считаются одним сервером.
2. Периодический проход подписей и времени замера выполняется для открытого
   экрана серверов. При открытии этого экрана подписи обновляются сразу.
3. Таймер списка соединений полностью останавливается, когда список скрыт,
   окно в трее или минимизировано. При возврате он включается, а список
   перечитывается. Активный экран сохраняет прежний темп 2/6 секунд и ускорение
   после изменения правил. Общий секундный таймер окна пока остаётся.
4. Сканирование каталога установленных программ начинается при фактическом
   показе списка соединений или явном открытии выбора программ. Создание
   невидимого окна при старте сразу в трей больше не запускает этот обход.
   Уже запущенное сканирование при скрытии не отменяется: повторное открытие
   получает готовый каталог, а не начинает сканирование заново.

Это изменения представления и его справочного списка. Защитный монитор,
TLS, DNS, WFP, протоколы, маршрутизация, параметры GC и бинарник Go-ядра
на этом этапе не менялись. SHA256 ядра остаётся
`B0285ED543D041578A78D489A4C83E6CEA37B335CB20D36EF40F591D99908ED3`.

## Полное WPF-окно

Добавлен --ui-resource-check в тестовую сборку. 600 синтетических профилей,
программный рендеринг, без принудительного GC. Прогрев 30 секунд перед главной
и 5 секунд перед следующими фазами. По 90 секунд: главная со списком соединений,
серверы, скрытое окно. Затем отдельная подтверждающая пара по 30 секунд на фазу.
Окна показаны без захвата фокуса: это видимое неактивное окно, а не активная
работа мышью. Подписки и VPN тестового процесса выключены; справочный список
соединений читает текущие таблицы Windows. Реальный TUN в стенде не создаётся.

Отдельные процессы до/после, одна машина. Меньше временных выделений не означает
такое же уменьшение постоянно занятой памяти. CPU процесса измеряется отдельно
от wall time; нельзя трактовать 100 мс CPU за минуту как 100% загрузки.

| 90 секунд | Выделения до → после | CPU до → после, мс |
| --- | ---: | ---: |
| Главная | 21 273 808 → 13 641 488 | 1453,125 → 3187,5 |
| Серверы | 10 637 736 → 2 229 888 | 156,25 → 93,75 |
| Скрытое окно | 155 696 → 146 600 | 109,375 → 62,5 |

Во время первого запуска «после» выполнялись оконные самопроверки. В измерениях
видны выбросы CPU на перерисовке, поэтому эта пара не доказывает снижение CPU.
Сравнение повторено после завершения оконных тестов:

| Повтор, 30 секунд | Выделения до → после | CPU до → после, мс |
| --- | ---: | ---: |
| Главная | 5 214 312 → 3 057 984 | 437,5 → 593,75 |
| Серверы | 3 550 832 → 729 776 | 78,125 → 125 |
| Скрытое окно | 57 400 → 57 400 | 15,625 → 46,875 |

Устойчиво подтверждено уменьшение временных выделений на экране серверов примерно
на 79–80%. Снижение общего CPU процесса **не подтверждено**: в повторной паре
CPU выше. Причина разброса не установлена; короткие фазы и текущая таблица
соединений Windows не дают надёжной оценки общего выигрыша. Округление CPU
на этой машине — 15,625 мс. Выборочно выдавать удачную первую пару за общий
результат нельзя. Большого снижения RAM этого этапа также не заявляется.

Медиана private working set экрана серверов в 90-секундной паре: 49,47 → 49,12
МиБ; в повторе 45,48 → 44,53 МиБ. Это малые изменения на фоне вариации запусков.
Прежние пользовательские 69 МБ этим измерением не заменяются.

### Изолированная стоимость обновления

В конце каждого прогона выполняются 1000 вызовов RefreshHome и обновления
подписей серверов. Измеряются CPU и выделения потока; отрисовка WPF и сетевые
операции не входят в эту серию. Это проверка стоимости конкретного кода.

| Показатель | До, два запуска | После, два запуска |
| --- | ---: | ---: |
| CPU, мс | 140,625 / 140,625 | 62,5 / 78,125 |
| Выделения, байт | 116 513 360 / 116 509 800 | 23 025 312 / 22 512 904 |
| Wall time, мс | 156,28 / 137,38 | 60,00 / 81,02 |

Именно этот участок стал дешевле на 44–56% по CPU и около 80% по выделениям.
Это не такое же снижение CPU всего клиента. При малом числе профилей эффект
меньше. Состав строк, события подключения и скорость обновления экрана сохранены.

MemoryProbe --core-steady держит 500 TCP-соединений к локальному echo-серверу.
90 секунд покоя, затем 90 секунд нагрузки: четыре потока по 16 КиБ с паузой
20 мс. Около 184 МБ передано через SOCKS в каждом прогоне. Сводка программ
опрашивается раз в пять секунд; диагностические счётчики читаются с той же
частотой. Сравниваются старое ядро 1003EFC… (до предыдущего этапа) и текущее
B0285ED…; новых изменений обработки пакетов в этом этапе нет.

| Фаза, 90 секунд | Старое ядро: CPU / выделения | Текущее ядро: CPU / выделения |
| --- | ---: | ---: |
| 500 соединений, покой | 31,25 мс / 2 473 784 байт | 15,625 мс / 1 285 760 байт |
| Локальный TCP-трафик | 2703,125 мс / 11 410 992 байт | 2843,75 мс / 10 084 616 байт |

Число опросов в первой фазе — 19 и 18 из-за границы таймера, под нагрузкой —

### CPU-профиль Go

Добавлен отдельный тестовый executable через go test -c. Только он понимает
переменную OBLACHKA_TEST_CPU_PROFILE: пропускает первые 105 секунд и записывает
60 секунд CPU-профиля под нагрузкой. Поставляемое ядро не содержит этого
переключателя или нового API профилирования. Обычный go test выполняется как раньше.

Из 1,28 секунды CPU-сэмплов за 60 секунд:

- 64,84% стеков проходят через connectionCopy и копирование TCP;
- 28,12% — через postCheckUpdate сетевого монитора и перечисление интерфейсов;
- сводка программ — около 0,78% сэмплов.

Большая часть выборки попадает в системные вызовы Windows. Это ориентир для
следующего исследования, а не основание отключать монитор интерфейсов или
обещать ускорение реального VPN. Нужны отдельные повторы и профили протоколов.

Дополнительно записан dotnet-trace полного окна. Его sampled-thread-time
показывает время стеков, включая ожидания; таблица с Wait/GetMessage не является
долей CPU. Это ограничение соответствует [описанию Microsoft](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/dotnet-trace).
Для численных сравнений выше использованы процессные CPU-счётчики без трассировки.
