# Следующие этапы

## 1. Сравнить базовый туннель с Throne

На отдельном тестовом профиле одного сервера сравнить Throne и RoutePilot с одинаковым ядром и параметрами. Нужны TCP/REALITY/Vision, XHTTP/REALITY, XHTTP/TLS с вашей реальной конфигурацией extra и downstream. Проверять успешные запросы, длительную загрузку, параллельные соединения, переключение Wi-Fi, сон/пробуждение и 30–60 минут работы. Личные профили автоматически не считывать.

Цель: воспроизводимая передача данных и корректное сообщение об отказах. Локальные тесты прототипа не заменяют этот этап.

## 2. Общесистемный VPN Windows

В 0.6.1 выделен интерфейс ITunnelController для окна и подбора. Целевая цепочка: UI → непривилегированный контроллер ядра → отдельный минимальный привилегированный helper для TUN, маршрутов и DNS. В 0.4 sing-box уже добавлен как второй адаптер для нативных VLESS/Hysteria2 профилей; общесистемный режим ещё не включён. Сравнить TUN закреплённых версий Xray и sing-box для TCP/UDP/DNS сценариев. Не связывать UI с JSON конкретного движка.

До интеграции определить атомарный жизненный цикл: снимок только изменяемых сетевых параметров → создание интерфейса → исключение адресов туннельного сервера из маршрута → установка маршрутов/DNS → проверка → точное восстановление внесённых изменений. UI crash, helper crash, отключение питания и занятый интерфейс должны иметь отдельные сценарии восстановления. Общесистемный fail-closed требует собственных правил firewall и проверки, а не только отсутствия DIRECT outbound.

Разрабатывать и тестировать изменения маршрутов на отдельной Windows VM. Не проверять на рабочем соединении пользователя, пока механизм восстановления не доказан.

## 3. Профили и подписки

Добавить профиль сервиса над существующей Remnawave: свой нормализованный список узлов, версии формата и ограничения возможностей ядра. Менять серверную панель для этого не нужно. Сначала проверить реальный пример ответа и HTTP-заголовки панели.

В 0.6.1 реализовано автоматическое запоминание списка, выбранного узла, ссылок и настроек с галочкой при импорте: Windows DPAPI, повторная валидация при загрузке, восстановление без автоматического старта. Проверены отсутствие открытых секретов в файле, повреждение шифротекста, смешанные ядра и восстановление выбора. Никакого экспорта секретов в обычную диагностику. Обновление подписки уже сохраняет прежний список при отказе и откладывает замену при активном туннеле. Далее — понятные ошибки срока действия, стабильные идентификаторы узлов и расписание обновлений.

## 4. Устойчивость клиента

Детектор живости через туннель, восстановление после сна/смены сети, ограниченные повторы с задержкой и jitter. Переход на другой узел делать явно и наблюдаемо. Недоступность одного сайта проверки не должна отключать весь VPN. Добавить тесты долгоживущих соединений и передачи крупных файлов.

## 5. Поставка

Проверенные официальные бинарники ядер, закреплённые версии и хеши, лицензии, подпись приложения/helper, установщик, обновления с проверкой подписи и откат. Сначала небольшой закрытый тест, затем расширение аудитории с метриками отказов без адресов, токенов и содержимого трафика.

## 6. Android и протокол

На Android использовать собственный UI, Android VpnService и готовый совместимый core. Общими должны быть модель профиля, формат API сервиса, состояния соединения и тестовые сценарии; Windows WPF-интерфейс переносить не требуется.

Эксперименты с транспортом вести отдельным стендом и возможностью возврата к стандартному VLESS/XHTTP. Сначала измерить конкретные проблемы: блокировка точки входа, неудачный REALITY target, задержки CDN, нагрузки на узел или панель. Новый протокол сам по себе не скрывает публичный адрес входа и не решает балансировку сервиса. Remnawave остаётся управляющим слоем, пока в ней можно описать необходимые узлы/профили; при собственном wire protocol понадобится адаптер и совместимый серверный компонент, а не обязательная полная замена панели.

В 0.6.2 реализованы журнал сетевой сессии и модель отката без изменения сети. В 0.7 добавлены IPC, контроль владельца и асинхронный координатор. Следующий шаг: результаты TUN-эксперимента на отдельной Windows VM, затем реальный Windows backend, установка helper и подключение системного режима к окну. Подробный порядок и критерии приёмки — [SYSTEM-TUN-ARCHITECTURE.md](SYSTEM-TUN-ARCHITECTURE.md).

## Состояние после 0.8

Без реального TUN выполнены клиентские блоки: фоновая проверка и ограниченное восстановление, расписание подписок и заголовки тарифа, сохранение выбора после смены ключей, измерения через отдельное ядро, обезличенная диагностика, сохраняемые черновики сайтов/программ, жизненный цикл процесса helper, локальная установка/обновление/откат и проверка подписанного манифеста. Описание границ — CLIENT-BLOCKS-0.8.md и DELIVERY-0.8.md.

Остаётся провести VM-эксперимент по vm-kit/START-HERE.md и vm-kit/README.md. Затем реализовать реальный Windows backend/helper с UAC, объединить сайты и программы в план системной сессии, подключить TUN к окну и доказать сетевой откат. Для публичной поставки нужны постоянный офлайн-ключ выпуска, Authenticode и автоматическая доставка обновлений с закреплённым ключом. Подписанные тестовые ZIP используют только временный тестовый ключ.
