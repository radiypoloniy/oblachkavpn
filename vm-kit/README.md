# Комплект проверки на Windows VM

Это экспериментальный стенд TUN sing-box, а не готовый привилегированный helper. IPC и журнал пока проверены с подменным backend; связь этих частей с реальными маршрутами требует следующей проверки на VM. На рабочем компьютере TUN не запускать.

1. Создать Windows 10/11 x64 VM, установить **.NET 10 Desktop Runtime x64** ([официальная страница](https://dotnet.microsoft.com/download/dotnet/10.0)), сделать снимок. Клиент собран под .NET 10 начиная с 0.9: на .NET 8 он просто не запустится. Скопировать весь распакованный комплект. Открыть приложение и запустить обычный SOCKS-профиль собственного тестового сервера.
2. Записать показанный приложением порт SOCKS и точные IPv4/IPv6 входного узла. Для этого стенда используйте IP в адресе профиля с исходным TLS SNI. Домены без закрепления IP и отдельный XHTTP downstream пока не подходят. Не копировать сюда UUID, пароль или ссылку подписки.
3. Проверить конфигурацию без изменения сети:

```powershell
.\vm-kit\test-tun.ps1 -SocksPort 10808 -PeerAddresses @('192.0.2.1')
```

Адрес 192.0.2.1 — документационный пример: заменить IP своего тестового узла. Команда генерирует новую папку vm-lab-*, конфигурацию без ключей и запускает только sing-box check. Ничего не удаляет.

4. На VM, в PowerShell от администратора, запустить эксперимент:

```powershell
.\vm-kit\test-tun.ps1 -SocksPort 10808 -PeerAddresses @('IP_ТЕСТОВОГО_УЗЛА') -Run -AcknowledgeDisposableVm
```

Перед -Run скрипт требует подтверждение одноразовой VM, проверяет модель виртуальной машины, права администратора и хеш sing-box. Проверка модели — защита от случайного запуска, не граница безопасности. Поддержаны стандартные названия Hyper-V, VMware, VirtualBox, KVM/QEMU и Parallels; другие VM пока не запускать этим скриптом.

## Особенность этой машины

На компьютере владельца постоянно включён собственный VPN, и выключить его нельзя. Гость выходит в сеть через NAT хоста, то есть его «обычный» выход — это выход хостового VPN, а не провайдера. Из этого два правила:

1. Базовый выходной адрес измеряется в каждом прогоне, а не берётся из прошлых записей. Команда `--system-tunnel-check` делает это сама и сравнивает с ним.
2. Узел для проверки нужно выбирать так, чтобы его адрес входа не совпадал с текущим выходом машины. Если совпал, выходной адрес не изменится независимо от того, работает туннель или нет, и перенаправление по IP доказать нельзя. Команда предупреждает об этом в отчёте.

Независимый от этого признак — захват трафика снаружи гостя: он показывает, куда гость реально шлёт пакеты, и от настроек хоста не зависит.

## Матрица

Проверять TCP IPv4/IPv6, DNS, длительную загрузку, параллельные соединения, выключение локального SOCKS, Ctrl+C, завершение sing-box, сон/пробуждение, смену uplink, перезапуск VM. Каждый аварийный сценарий начинать с восстановленного снимка. UDP/QUIC заблокированы первой конфигурацией — это ожидаемый предел, не поддержка игр.

Для браузера использовать обычное соединение без вручную заданного SOCKS. На контролируемом сервере проверить адрес TCP-подключения; DNS проверять независимым захватом трафика VM. Отсутствие DIRECT outbound само по себе не доказывает отсутствие утечек. strict_route не заявляется как проверенный kill switch.

После Ctrl+C скрипт проверяет только собственный интерфейс. StoppedInterfaceAbsent не является доказательством полного отката всех DNS/firewall/маршрутов. NeedsManualReview требует отката снимка. Никакого автоматического удаления чужих объектов или восстановления широкого снимка сети нет.

Если ядро требует драйвер, не скачивать случайную DLL. Зафиксировать отказ и использовать официальный источник с проверкой происхождения; поставка драйвера и установка helper ещё не завершены.

Сохранить run-status.json, версии ядра/ОС и результаты матрицы без профиля, ключей и подписки. Этот результат нужен, чтобы выбрать реальные API владения интерфейсом и маршрутов, реализовать Windows backend и включить системный режим в приложении.

Конфигурация подготовлена по официальным схемам [TUN](https://sing-box.sagernet.org/configuration/inbound/tun/), [SOCKS](https://sing-box.sagernet.org/configuration/outbound/socks/), [DNS HTTPS](https://sing-box.sagernet.org/configuration/dns/server/https/) и проверена бинарником sing-box 1.14.3. Пока выполнена проверка синтаксиса, не реальная передача через TUN.

## Разбор захвата трафика

Вопрос «не уходит ли что-то мимо туннеля» решается только захватом снаружи гостя: то, что система сообщает о себе изнутри, доказательством не является. Захват снимает сам гипервизор.

```powershell
VBoxManage modifyvm "VPNTests" --nictrace1 on --nictracefile1 C:\lab\run.pcap
# ... прогон с поднятым туннелем ...
VBoxManage modifyvm "VPNTests" --nictrace1 off
.\vm-kit\parse-capture.ps1 -Path C:\lab\run.pcap -Peer IP_ТЕСТОВОГО_УЗЛА -Needle @('216.239.35.0')
```

В `-Needle` перечисляются адреса, которых в кадрах быть не должно: если внутри гостя обращались к UDP-серверу, а его адрес в захвате не встретился, значит обращение шло внутри туннеля. Адрес узла из `-Peer` служит контролем — он обязан встречаться много раз, иначе захват снят не в том окне.

Край окна скрипт определяет по обмену с узлом и берёт его с запасом: пока туннель снимается, обмен ещё идёт, а трафик уже уходит напрямую. Точную границу видно по таблице темпа, после чего окно задаётся через `-WindowStart` и `-WindowEnd`. Решающая строка вывода — число новых соединений мимо туннеля: SYN без ACK внутри окна означает настоящую утечку, а остальные кадры могут быть продолжением сокетов, открытых до включения.

## Проверка блокировки трафика мимо туннеля

Каждый сценарий — с восстановленного снимка, с включённым брандмауэром Windows в госте и под захватом `nictrace`, как выше. Внутри гостя всё время работает фоновый генератор, иначе захвату нечего показать:

```powershell
while ($true) { try { Invoke-WebRequest https://example.com -UseBasicParsing -TimeoutSec 3 | Out-Null } catch {}; w32tm /stripchart /computer:216.239.35.0 /samples:1 /dataonly | Out-Null; Start-Sleep 1 }
```

Включение — обычным окном приложения: системный режим в настройках, «Подключить».

1. **Края окна.** Подключить, 60 с работы, «Остановить». Мимо узла внутри окна — ноль новых соединений (SYN без ACK).
2. **Смерть ядра.** При поднятом режиме `taskkill /f /im xray.exe` (для Hysteria2 — процесс sing-box окна, не помощника). Ожидается: пояснение «Связь с сервером прервана… заблокирован», в захвате — ни одного кадра мимо узла, пока ядро мертво; через несколько секунд ядро поднимается само, туннель не пересоздаётся.
3. **Ядро не может вернуться.** Отключить сеть узла (например, запретить его адрес на роутере стенда) или выбрать заведомо мёртвый узел из запасных. Ожидается удержание без утечки до нажатия «Остановить»; после «Остановить» сеть возвращается.
4. **Смерть окна.** Завершить `Oblachka.exe` из диспетчера. Помощник сам снимает сессию — это известная граница до появления службы: утечки после снятия ожидаемы и фиксируются отдельно, но окно между снятием туннеля и снятием блокировки должно быть пустым.
5. **Чужое разрешение.** От администратора добавить разрешение для одной программы и проверить, пробивает ли оно блокировку на краях окна:

```powershell
New-NetFirewallRule -DisplayName 'lab-allow-curl' -Direction Outbound -Program "$env:SystemRoot\System32\curl.exe" -Action Allow
# во время шага 2 (ядро убито):
curl.exe -m 5 http://1.1.1.1/
Remove-NetFirewallRule -DisplayName 'lab-allow-curl'
```

   В `-Needle` разбора захвата добавить `1.1.1.1`. Пока туннель поднят, запрос обязан уйти в туннель (маршрут), а не мимо. Ответ на вопрос, нужен ли WFP до закрытого теста, даёт именно этот шаг: если `curl` проходит мимо, блокировка брандмауэром для строгого режима недостаточна.

Сценарии 2 и 5 `--system-tunnel-check` выполняет сам: завершает ядро и пробует `curl` к адресу узла без правила и с правилом. Строка «чужих включённых разрешений» показывает, сколько таких правил в госте и есть ли среди них правила без привязки к программе.
